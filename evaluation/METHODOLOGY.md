# 行业对照、升级路线与通用 Agent 自动评测方法论

资料核对日期：2026-11-17。项目现状见 [总览](HANDBOOK.md)。外部体系用于选择工程方法，不用于宣称本项目达到其榜单水平。下面按研究问题与项目适配性选取国内外各三项代表工作，不给无法比较的“最好公司”排名。

实施进展：证据截断、预算耗尽重试、最终支持状态反馈和并发卡片超额已修复；失败合并复评、审核、版本入库、回归及效果追踪已实现。下文升级建议包含实施前的动机，最新结果和剩余质量限制以 [实施记录](COMPLETION-RUNBOOK.md) 为准。

## 1. 国内三项代表方法

### THUDM / AgentBench：在交互环境里检查执行

AgentBench 用多种交互环境评测模型作为 Agent 的表现，强调动作、反馈与任务结果，不能把文字回答能力等同于执行能力。[官方实现](https://github.com/THUDM/AgentBench)

项目相同点：主评测进入生产 startNewsSweep，观察真实工具执行与数据库终态。区别：项目是窄领域七题，环境是冻结资料，不是广泛环境能力基准。可借鉴：统一环境 reset/step/observe 契约，增加工具格式错误、不可达状态和预算耗尽的单独归因；每题先验证存在可行解。

### 阿里通义及合作团队 / WebWalkerQA：检索命中不等于完成取证

WebWalkerQA 测试网页子页面遍历、深入信息提取，说明只搜到入口页面仍可能找不到答案。[原论文](https://arxiv.org/abs/2501.07572)

项目相同点：曾遇到正确材料未读到关键段落，增加分页/查找。区别：当前冻结候选正文已准备好，不测试开放网络的多跳导航。可借鉴：另建真实网络或可回放链接图套件，分别测入口命中、证据可达、证据实际读取、答案交付。不能把当前分页改进宣称为网络浏览能力提升。

### 红杉中国 / xbench-DeepSearch：中文难题与持续题库更新

xbench-DeepSearch 的官方报告强调中文互联网深度搜索任务、专家制题交叉核验，以及持续更新和保留题机制。[官方报告](https://xbench.org/files/Leaderboard%20Report%20xbench-DeepSearch_202505.pdf)

项目相同点：关注中文技术事实、保留首次曝光和使用范围。区别：本项目题目/标签主要由模型辅助建立，七题已经反复暴露，缺少独立验收题池。可借鉴：按事件簇与时间切分，加入中文首发、英译中、二手转述、版本冲突等切片；正式发布评估在新题上做，不把开发回归当成盲测。

## 2. 国外三项代表方法

### Anthropic：task、trial、grader、轨迹和最终结果分开

其 Agent 评测指南强调组合确定性、模型与人工评分，并区分任务、重复试验、运行过程和环境最终结果。[官方指南](https://www.anthropic.com/research/demystifying-evals-for-ai-agents)

项目相同点：任务/试验/评分产物分离；规则检查和语义检查组合；评分器也有校准。区别：当前标签和评分缺乏独立性；缺少线上反馈与离线基准的系统联动。可借鉴：每个评分维度做反例测试、误放行审计，建立“评分器不确定时转复核”的工作队列。模型辅助替代人工是本阶段选择，不能改变标记冒充真人评审。

### OpenAI / BrowseComp：把难检索与易核验分开

BrowseComp 测量难以找到的信息定位能力，题目通常最终答案简短，并研究额外计算投入的影响。[官方介绍](https://openai.com/index/browsecomp/)

项目相同点：每题分解成可核验事实，而非只给整张卡一个印象分。区别：本项目冻结证据降低搜索不确定性，且额外要求引用与状态正确。可借鉴：把答案正确率、证据支持率、两者联合通过率分别报告；研究预算增加后的质量/费用曲线，避免“多花钱”直接当作能力提升。

### Sierra / τ-bench：终态和多次可靠性

τ-bench 在用户与工具交互场景中检查业务目标，并通过重复试验研究可靠性。[官方代码](https://github.com/sierra-research/tau-bench)

项目相同点：检查数据库终态、卡片数量、重放不重复。区别：没有复杂模拟用户的多轮纠正和政策约束覆盖，现有三次实验不足以估计稳定性。可借鉴：为每个任务定义允许变更与禁止副作用，并用独立重置的多次试验观察稳定交付。仅末态正确可能掩盖中途违规，必须结合操作日志。

## 3. 与评测平台的异同

LangSmith 将离线 benchmark/regression 与在线监控分开，并支持代码、模型及组合评估器。本项目已有离线运行、复评和基础追踪，但缺少托管的线上采样、标注队列、跨版本可视化与告警运营。[官方评测分类](https://docs.langchain.com/langsmith/evaluation-types)

ModelScope EvalScope 提供可扩展的评测框架与多类模型评测入口。项目当前专用 TypeScript runner 更贴近自身持久工作流，但跨 Agent/模型/工具生态接入成本更高。未来可对接通用框架做外部任务适配，保留本项目证据和业务状态检查，不必为了换框架重写所有业务断言。[官方仓库](https://github.com/modelscope/evalscope)

本项目的价值在可验证副作用、引用追溯、生产入口一致性和成本边界；短板在任务覆盖、评审独立性、线上代表性与实验统计设计。框架名称本身不能解决这些短板。

## 4. 优先升级路线与验收条件

### P0：确认真实云端失败原因

首轮取证见 [失败分析](CI-FAILURE-43907971612.md)。唯一失败 pilot-04；确认单项研究预算耗尽、缺 findings、证据验证默认只取前 6000 字符及无效恢复重试。归因、行为修复和后续真实回归均已执行；保留下面的流程供新的失败使用。

输入：运行 43907971612 的 artifact。按 preflight、执行、结构、语义、provenance/输入 hash 分类排查。现有证据只确定严格门禁失败。

交付：逐题根因、原始日志与最小回归；若是软件问题先离线修复，若是模型偏题保留失败样本；不放宽基线获得全绿。验收：同样冻结输入可解释失败，修复对应测试通过，再做必要的一次真实验证。

### P0：补全费用与长期调度控制

当前工作流成本不总包含评分费用，DeepSeek 无经验证的硬美元封顶。增加生成/研究/Jev/coverage/grounding 统一成本账，记录未知价格和实际解析型号。为每日运行建立月度累计阈值和停止策略；客户端预估停止有并发/价格误差，只有供应商强制额度才可称硬封顶。

验收：任意报告能说明已知费用、估算费用、未知费用及缺失调用；额度不足时不发新调用；到期密钥与调度停用可被发现。

### P1：扩展任务覆盖及独立评审

建议先按风险与业务频率收集多种独立事件，数量由期望检测的退化幅度和预算决定，不承诺随意的“100 题足够”。保留当前七题做快速冒烟；另外建立新的验收集。每类覆盖正常、空结果、冲突证据、证据不足、长文、工具异常、越权输入。

同模型 judge 继续用于快速开发；引入不同模型家族的盲评抽查，争议样本独立复核。不同模型不自动等于真人标准，仍要测一致性/偏好偏差。项目当前允许模型辅助记录，只有真的有人员判断才能将 humanReviewed 置为 true。

验收：新题的事件簇与开发集分离；gold 来源记录完整；分别报告错误放行率和误拒率，阈值按业务风险预注册。

### P1：公平验证候选策略

固定模型、证据、题面、评分器与总资源规则，交错/随机安排 K=1/2/3；记录实际选择数、实际研究数、成功率、延迟和完整费用。给每题相同重复数，不因失败选择性重跑。单独测召回、研究和发布选择。

验收：按任务/事件簇配对分析，有效样本量与置信区间可追溯。明确预算是“每候选相等”还是“每任务相等”：两者回答不同问题，不可混用。

### P1：让失败回流真正进入数据闭环

将生产使用中的用户纠正/不满意、工具异常、成本异常与低置信答案纳入候选队列；同时抽样成功案例，避免只学失败分布。对齐原始评分与复评状态，去敏、事件去重、确认可解性、添加参考证据、新版本发布，再观察修复是否减少线上同类问题。

验收：每个新回归题能回链至事件，标签有来源和审查，版本变更可回滚；自动导出不是自动 gold。修复前后线上指标与失败率有对照，才称飞轮产生效果。

### P2：真实环境、安全和恢复常态化

新增动态网络独立套件，允许网页变更但保存抓取证据；安全测试记录攻击是否实际被读取、目标是否可达，避免“没碰到攻击”也算防住。把真实进程崩溃/恢复、旧 epoch 写入、重复发布及取消纳入定期完整测试；目前每日七题不覆盖全部专项。

同时增加模型别名漂移监测、跨运行趋势与长期归档，评审正文过度概括和多来源组合支持。评审器自身遇到提示注入必须有防护测试。

## 5. 通用 Agent 自动评测构建方法论

本节是依据本项目经验与上述资料综合形成的设计方法，不是外部组织统一发布的标准。

### 第一步：先定义业务成功合同

描述“触发条件—应完成动作—最终状态—不可发生副作用”。例如客服退款应检查退款到账与订单状态；代码 Agent 应检查测试与仓库变更；检索 Agent 应检查事实、引用、来源范围。答案流畅只是一个维度。

产物：任务 schema、验收断言、风险分层、任务合法终态。允许正确拒绝、澄清、无结果，不能强迫每题生成内容。

### 第二步：搭建可重置环境

为任务提供独立初态、工具权限、资源上限和确定的观测接口。冻结环境用于可重复回归，真实环境用于外部有效性，两条线分别报告。恢复测试要真触发故障点；模拟器的通过只验证模拟条件。

产物：environment.reset、run、snapshot、cleanup 适配层；凭证隔离；可解性验证。工具调用轨迹不必与参考逐步一致，只要约束和目标都满足。

### 第三步：建设版本化任务数据

每题至少包括 ID、题面、来源与版本、环境初态、参考证据、成功/失败断言、资源预算、分组与曝光时间、标签来源。训练/开发/验收按事件或来源簇切分，不能对近重复文档随意逐行随机切分。

产物：可校验的任务包和 manifest；不可覆盖的版本；抽样规则与标签审查记录。参考答案可不唯一，参考事实和状态约束必须清楚。

### 第四步：记录全过程，但只保存必要数据

记录 taskId、trialId、版本 hash、实际模型、工具输入输出、耗时、请求/用量/费用、终态、引用和副作用；记录缺失和未知，不默认零。去敏、授权与保留策略从采集时就开始。

产物：统一 observation 和 trace；隔离试验；幂等与恢复断言。不可从最终输出反推从未观测到的内部行为。

### 第五步：分层评分

顺序建议：执行有效性 → 硬规则 → 语义质量 → 业务偏好。技术错误单列但仍计入全计划任务的可靠性；硬约束失败不被平均高分抵消。

代码评分处理类型、schema、终态、工具权限、引用位置；模型评分处理改写、事实覆盖、蕴含、语气与偏好；独立复核处理歧义和评审器校准。对高风险场景，是否必须人工判断由产品风险策略决定。

产物：每项 verdict、证据、理由、不确定性与责任模型版本。禁止只有一个无法定位原因的总分。

### 第六步：先测评分器，再测 Agent

构造正反例：同义改写、遗漏子事实、错误否定、引用错位、真引用假结论、相关但偏题、保留限定与过度推断、注入评分器。必须同时覆盖“错却放行”和“对却拒绝”。

可采用 false acceptance = 错误样例中被放行数 / 错误样例数，false rejection = 正确样例中被拒绝数 / 正确样例数，另报 uncertain/technical_error。不能仅报 accuracy 掩盖多数类或故障。

### 第七步：预注册实验与决策规则

固定主指标、失败分母、预算、模型、题库、重复次数和停止条件。按风险检查 Pareto 关系：质量增益是否值得额外时间/费用。分别观察：

- 计划任务成功率：成功试验 / 全部计划试验，保留未完成与技术失败。
- 有效环境条件下成功率：另列剔除规则及数量，不能隐藏环境失败。
- 多次可靠性：同一任务 k 次均成功的比例，与至少一次成功不同。
- pass@k：多次尝试中至少一次成功；适合可选择结果场景，不等于用户一次请求可靠性。
- 成本/成功任务：总执行与评审成本 / 成功任务数，失败尝试也计入；零成功时未定义。
- 延迟 p50/p95：足够样本才解释尾部延迟；同时报告超时。

选择候选 Top-K、采样次数 k、工具预算是不同自变量。无独立性时不把同题 100 次当成 100 个独立业务任务。

### 第八步：自动执行与发布门禁

PR 快速免费检查；按需/定时付费固定基准；周期性扩大任务覆盖、安全恢复和隐藏题。检查不完整应失败关闭。报告、artifact 和实际运行必须绑定同一源码/数据/评分协议。

产物：CI workflow、预算准入、退出码、报告、通知、回滚流程。CI 红灯阻止自动发布的规则要在仓库/部署系统显式配置。

### 第九步：建立线上与离线的连接

线上反馈 → 采样去敏 → 复核归因 → 去重新任务 → 校准标签 → 新基准 → 改进实现 → 对照评测 → 发布 → 线上观察。

每个箭头都要有状态和负责人；可以自动化采样与初筛，但不能把预测直接作为真值循环强化。成熟数据飞轮必须证明：修复进入产品，并减少了实际用户同类失败。

### 第十步：持续审计测量有效性

定期问：题目是否代表用户？模型是否看过答案？judge 是否随版本漂移？环境是否可解？指标是否诱导错误优化？成本是否漏算？失败是否被重试隐藏？

产物：数据卡、评测卡、已知局限和变更历史。把这些与报告一起交付，避免把一次高分当成永久能力。

## 6. 可迁移任务合同示例

以下是通用设计示例，不是本仓库可直接加载的新 schema：

```json
{
  "taskId": "refund-001",
  "version": 1,
  "goal": "对符合政策的订单退款一次",
  "environment": {"snapshot": "orders-v1", "clock": "frozen"},
  "allowedTools": ["lookup_order", "refund"],
  "assertions": ["refunded_amount_equals_eligible_amount", "refund_count_equals_one"],
  "forbiddenEffects": ["modify_other_orders", "expose_credentials"],
  "budget": {"maxToolCalls": 12, "timeoutSeconds": 120},
  "label": {"origin": "reviewed_policy", "humanReviewed": false},
  "partition": {"eventGroup": "order-policy-family-A", "usage": "development"}
}
```

把上述合同替换成自己的业务对象，配上环境重置、实际输出观测、分层评分和版本门禁，就有最小可用体系；之后用真实失败扩展覆盖。不要先购买平台或堆大量题目，再回头猜成功意味着什么。
