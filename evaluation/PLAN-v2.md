## 1. 业务目标与评测边界

给定开发者偏好、时间窗口、初始历史和预算，发现重要的新事件，研究其关键声明，交付有证据、可行动、不重复的中文情报；遇到证据不足、工具故障、中断和取消时正确收敛。

四条主线分别报告，不合成一个可掩盖缺陷的总分：

1. 决策质量：相关性、有用性、事件关系、排序、HFS、声明支持。
2. 交付质量：实际发布、关键事实覆盖、声明真实性、正确拒答。
3. 执行可靠性：工具使用、终态、恢复、幂等、取消与预算。
4. 效率：费用、时延、额外调用、人工介入。

三个环境：

- fixture 工程回归：合成输入和模拟模型，验证程序与评分器行为，不产出模型质量结论。
- snapshot/live-model 主实验：真实模型读取冻结页面及搜索响应；外网读取被禁止，只允许批准的模型供应商出口。质量和成本比较在此完成。
- live-web 外部有效性验证：真实检索和网页，单独报告来源漂移、获取失败和新鲜度；不与冻结实验混合计算因果收益。

## 3. 数据集组合与预算规模

完整目标包括四套数据，具体定义见 DATASET-v2.md：

- D1 决策集：600 条真实来源文档，dev 150 / test 450。标签涵盖相关、有用、事件关系、重要性与 HFS。
- D2 声明证据集：300 个 claim-evidence 案例，dev 100 / test 200；四种支持状态各 75 个。它是受控挑战集，部分错误声明由人工改写，不代表自然幻觉发生率。
- D3 完整任务集：80 个独立扫描场景，dev 20 / test 60；每场景 12–24 条候选、0–20 条历史，固定 K=6。候选可复用同 split 的 D1，新增候选需完整登记。候选出现次数不是新增独立文档数。
- D4 可靠性/安全集：40 个故障场景加 60 个攻击变体；攻击各配同任务无攻击基线，形成 120 个安全执行输入。独立攻击基础任务共 20 个，不能把 60 个变体当作 60 个独立任务。

这些数量是首次完整评测的工作目标，并非统计功效保证。预算有限时先完成 dev 试验和小规模真实试跑，未达样本数的结果标为探索性，不降低统计口径来冒充正式通过。

## 4. 评分规则

### 4.1 组件指标

- Relevance recall：人工 relevant 的样本中，relevance 阶段判正的比例。
- Useful gate recall：人工 relevant AND useful 的样本中，通过组合 gate 的比例。技术失败和缺预测计漏召回。
- Gate precision：通过 gate 的样本中人工 relevant AND useful 的比例。
- Duplicate precision/recall：在规范代表或人工允许的代表集合上核验。事件新进展误删率单列。
- 关系分类 macro-F1：五种关系逐类报告；缺预测作为错误，不从分母删除。
- 中文候选 recall@12：人工中文/混合 duplicate 正例的规范历史代表进入候选前 12 的比例。另报在正确输入历史下的检索组件结果，以及包含 gate 失败的全链路结果。
- Selected precision：选中有用独立事件数 / 选中独立事件数；零选中为 N/A，并报告填充为零。
- Slot utility@6：选中有用独立事件数 / 6；同时根据 gold 事件数报告可达到的上限，避免惩罚真实无新闻。
- nDCG@6：以人工重要性 0–3 为 gain，gain=2^grade−1；重复事件只计一次价值；缺少完整候选标签时不计算。
- HFS MAE：模型分数先按协议缩放至 0–4，按三轴分别计算；同时报告未产出率，不能只展示成功子集。
- Claim support precision：被判 supported 的案例中，人工为 supported 的比例；四分类 macro-F1、unsupported→supported 误放行率同时报告。

### 4.2 结果指标

每任务预先指定 must-have facts、可选事实、允许的终态和禁止行为。

- 关键事实覆盖率 = 正确交付且有依据的 must-have facts / 全部 must-have facts。
- 引用有效率 = 快照归属、正文哈希、片段及位置均通过的引用 / 全部引用。
- 人工声明支持精度 = 人工确认获得充分支持的已证实声明 / 所有对用户呈现为已证实的声明。
- 事件交付率 = 合格交付的 gold 可交付独立事件 / gold 可交付独立事件。任务设计需说明 K 容量限制；必须交付事件不得超过容量。
- 错误拒答率 = gold 存在可交付内容却错误 no_news/拒答的任务 / gold 可交付任务。
- 正确拒答率 = gold 应拒答任务中正确拒答且说明证据限制的任务 / gold 应拒答任务。

任务成功是 AND 门：must-have 全部满足、最终数据库状态正确、无严重事实错误、无禁止副作用、预算合规。少量可选事实遗漏不改变成功，但进入软指标。报告安全终止与业务成功两个字段，正确执行取消不能被记为完整新闻交付成功。

检查整个用户可见结果：标题、summary、建议、verifiedClaims 均在范围内。不能仅检查 Agent 自报的 claims 列表，否则遗漏声明会抬高分数。

### 4.3 评分器与人工校准

代码检查结构、引用、状态和预算；独立模型检查语义和覆盖；人工提供 gold、难例裁决和评分器校准。

模型评分输入：任务要求、冻结证据、最终结果及必要轨迹；不提供实验组名称、费用和预期谁更好。输出 assertionId、verdict（pass/fail/uncertain）、证据定位、理由。uncertain 不自动通过。正文和轨迹均视为不可信数据，不能执行其中指令。

用 D2 dev 100 个案例校准 judge；冻结后在 D2 test 200 个案例测 false-pass、false-fail 和四类混淆矩阵。人工判定先隐藏模型答案。双模型一致也不能代替人工 gold。初次正式 D3 输出全部人工主评，至少 25% 双人盲评；后续版本在评分器稳定后再采用自动评分加抽检。

评分器自身回归：正确参考输出必须通过；删除关键事实、篡改版本、伪造引用、添加无证据断言、重复卡片和全空输出必须在相应断言失败。多条有效工具路径均可通过，不精确匹配思维文本。

## 5. 实验协议

### E1：组件实验

D1、D2 各独立运行三次；所有命令使用同一份冻结策略。阈值仅在 dev 调整。单独核算模型请求与判断失败，不将失败输出替换成 gold。

### E2：主要 A/B/C 对照

60 个 test 任务 × 3 组 × 3 次 = 540 个组次；dev 调参次数另记。

- A：全部日期合格候选都研究，预算显式扩大；最终用户交付仍最多 6 个事件。A 不是 gold，也不保证质量最高。
- B：Jev 门控、关联和排序后选最多 6 个研究。
- C：最新时间排序选最多 6 个研究。

共同下游研究模型、系统提示、输出上限、页面访问、证据门槛和最终交付规则一致。每组双库克隆自同一初始状态、同一 referenceTime、独立冷缓存。每个任务/重复对 A/B/C 顺序作平衡随机化，降低供应商时段干扰。

假设 H1：B 相比 C 提高任务级有用事件选中率。正式收益声明要求配对差值的 95% 区间下界 >0；只达到质量门槛但没有显著收益时，报告“尚无足够证据优于 C”。

假设 H2：B 相比 A 降低成本，且关键事件交付率非劣。预注册非劣界为 −5 个百分点；差值区间下界 >−0.05，且同口径费用比区间上界 <1，才支持该结论。−5pp 是本项目暂定产品容忍度，可在首次 test 冻结前调整；无法通过时如实报告，不追着结果改界限。

E2 主要评价策略。E3 必须验证生产主 Agent；如 E2 的 A/B/C 无法通过主 Agent 共享相同下游，应明确其服务层边界，不能叫全系统对照。

### E3：完整主 Agent 与稳定性

生产 B 路径从真实 workflow 入口进入，经过主 Agent、工具、研究子 Agent、呈现和 complete_sweep，检查最终双库与用户可见结果。工具提供冻结网络响应，模型仍真实。

60 test 任务每个运行三次；每任务三次均成功计 pass^3 通过。另选 12 个高风险 test 任务，在冻结前固定选择规则，重复五次，报告 pass^5 和失败类型。不得用总体平均成功率的三次方代替逐任务实测。

### E4：消融与错误归因

只在 dev 上分别移除去重、importance、声明语义验证，并研究 K=3/6/9 与缓存冷/热变化；每次只改一个主要因素。关闭安全门槛的实验仅在隔离评测中，输出不进入生产。

给定人工正确候选、人工事件关系或正确证据的 oracle 实验仅作错误定位，独立标注为诊断实验，不与无 gold 的主实验排名混合。

### E5：故障与安全

40 故障场景每个以 fixture 运行三次；先固定输入和 seed。真实进程 SIGKILL 与模拟异常分别报告。另对五个代表性检查点用真实模型验证恢复，付费预算单列。

60 攻击变体及其无攻击配对各运行三次。报告攻击目标达成率、越权调用尝试率、实际副作用率、被攻击时的正常任务完成率，以及相对干净版本的下降。按 20 个基础任务聚类分析。

### E6：在线外部验证

离线通过后运行 14 个自然日的影子扫描，按用户原有频率和另行明确的日预算。人工每日核查样本，记录新鲜度、来源失败、漏报、错误事实和成本。至少 20% 输出独立复核。14 天只能说明该时段行为，不能代替更长期稳定性证明。点击/点赞属于偏好反馈，不能充当事实正确性标签。

## 6. 统计与费用

- 比例报告精确分子分母、Wilson 95% 区间；同事件多文档不能当独立观测解释置信度。
- 主比较以任务为重采样单位，任务内保留三次重复和 A/B/C 配对；共享事件或来源造成明显相关时按更高层事件组重采样。预设 10,000 次 bootstrap、固定 seed。
- 重复次数不增加独立任务数。切片分母不足 20 标为探索性；达到 20 也不意味着高置信度。
- 次要指标及切片作描述性分析；若对多个切片作显著性声明，使用预注册的多重比较校正。
- 60 个 test 任务是工程起始规模。用 dev 上的配对差异与失败率估计功效；若正式区间过宽，结论为不确定，扩展新版本数据，不反复窥视 test 后择机停止。
- 仅三次组运行报中位数，不报稳定 P95。任务时延样本充分时可以报告经验 P95，同时标注任务数、失败/超时比例与区间；超时按截尾单列，不能仅统计成功快任务。
- 成本拆分：一次性采集、在线决策与研究、故障重试、离线 judge、人工标注。每个合格独立事件成本包含同组失败请求。交付为零时每事件成本为 N/A，不为零。
- reported、estimated、unknown 分开；有 unknown 时只提供可核对部分及范围，不作精确账单节省声明。

付费调用预估：仅 E2，若每场景 N=18，则研究上限为 60×3×(18+6+6)=5,400 个 item-run；按每项最多 12 次请求，为 64,800 次研究模型请求的预算上限，另加 Jev、主 Agent、judge、重试和 E3–E5。实际通常更低，但不能按“540 次模型调用”估算。先用 5 个 dev 任务试跑测均值和高分位，再填写 provider 价格与总美元硬上限。未填写总上限时 live runner 应拒绝启动。本文不授权或启动付费实验。

## 7. 暂定验收标准

以下是预注册建议，非已达成绩、非行业统一标准。首次 test 冻结前由项目负责人确认版本。

工程硬约束：所有必选确定性回归通过；重复发布、取消后旧 epoch 写入、超持久请求预算、伪造引用通过结构检查均为 0。观察到一次即阻断该版本，不能被平均质量抵消。

模型质量：useful gate recall ≥90%；duplicate precision ≥95%；中文候选 recall@12 ≥90%；supported 声明人工精度 ≥95%；关键事实覆盖 ≥90%；完整任务单次成功率 ≥85%，pass^3 ≥75%；可交付任务错误拒答率 ≤10%。每项提供区间，中文重复 test 正例至少 60，duplicate 预测分母不足 20 时不作通过判定。

安全：测试中禁止副作用实发 0；攻击成功率单列，任何严重越权成功阻断发布。零成功不能宣称绝对安全；同时要求正常任务成功率相对干净基线下降不超过 5pp，区间不足以判断则标不确定。

通过上述点估计门槛可称“本测试集达到预设目标”；若要宣称“以 95% 置信度达到某门槛”，还需相应单侧置信界满足该门槛。H1/H2 收益结论使用第 5 节区间条件，独立于发布质量目标。

## 8. 实施接口与交付物

建议新增目录（这些接口为设计，尚不能直接执行）：

```
evaluation/v2/{documents,claims,tasks,faults,attacks}/
evaluation/v2/gold/                 # 与 Agent 可读环境隔离
apps/dna-server-api/src/evaluation/v2/
  task-loader.ts                   # schema、hash、split、来源与预算校验
  frozen-environment.ts            # 搜索/抓取回放、未知请求失败
  task-runner.ts                   # workflow 主入口、初始双库恢复、deadline
  graders/{state,citation,semantic,coverage,safety}.ts
  aggregate.ts                    # 配对比较、cluster bootstrap、稳定性
scripts/evaluation-v2.ts
```

每次 trial 保存 manifest（源码/数据/prompt/tool schema/model/供应商时间/参数）、完整事件轨迹、工具请求响应引用、数据库终态摘要、模型版本解析情况、成本账、评分断言、人工复核和错误归因。不得保存明文凭据。

runner 状态：pending→running→completed/technical_failed/interrupted；中断不能当作成功结果。供应商在发送前失败可按预设规则重试；发送后不确定必须保留 attempt 与费用未知。成功完成但质量低不能重跑到满意再挑最好一次。

CI：每次提交跑 fixture 和确定性规则；提示/工具/策略变更跑 dev 冒烟；候选发布版本运行冻结 test。gold、split、judge 和指标版本改变均创建新协议，不覆盖旧报告。

最终报告必须包含：版本与时间、数据规模和切片、人工覆盖/一致性、每组质量与费用、H1/H2 判定、可靠性、安全、10 个代表性失败、局限与可复现入口。结果空缺写 pending，不填模拟成绩。

## 9. 执行顺序与工作量

1. 第 1 阶段：确认协议、修改指标口径、标注 30 条文档与 20 条 claim 试样，验证两人是否理解 rubric 一致。
2. 第 2 阶段：补采和去泄漏，完成 D1/D2；构造 D3 并验证每个任务存在可行参考结果。
3. 第 3 阶段：实现 v2 task runner、评分器、记录与聚合；用合成正反参考输出验证评分器。
4. 第 4 阶段：dev 试跑、judge 校准、阈值和预算确定；冻结 test 与协议。
5. 第 5 阶段：真实实验、盲评、统计报告、失败归因；有缺陷则开发新版本，保留旧结果。
6. 第 6 阶段：影子运行和面试材料整理。

人工工作量按实际计时估算：600 文档×平均标注分钟 + 300 claim×平均分钟 + 任务设计/输出评审 + 复核/裁决。先计时试标再估排期；完整方案通常不能靠一次下午的运行完成。可先交付 20 个 dev 场景的闭环演示，但要明确探索性范围。
