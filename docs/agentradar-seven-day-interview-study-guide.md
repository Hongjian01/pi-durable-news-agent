# AgentRadar 七天秋招面试学习手册

版本日期：2026-10-28。适用对象：已经有 AgentRadar 项目简历，需要理解改造后的项目并准备口述面试的开发者。

## 使用方法与完成标准

这份文档既是学习计划，也是教材、练习册和答案册。每天按顺序完成“学习安排→知识讲解→问题自答→练习→闭卷过关”。必做部分不需要安装环境、运行项目、定位源码或修改代码。源码与验收文档只作核对材料，不要求背诵路径。免费演示为选做，不影响完成七天计划。

每天安排 150 分钟，共 17.5 小时：10 分钟复习、50 分钟学习、25 分钟问题自答、30 分钟练习、25 分钟闭卷过关、10 分钟纠错。第七天沿用相同时长，但替换为整合与模拟面试。

准备一个笔记文件，按 D1～D7 分区。每天留下三项记录：自己的问题答案、练习结果、闭卷口述得分。先写自己的答案，再展开参考答案；不要把照读答案当成掌握。

### 怎样使用“正确答案”

- **实现题**：状态、计算和机制有明确答案，应按本文与当前代码核对。
- **设计题**：不存在唯一措辞，本文给出合格答案及必须包含的逻辑，不要求逐字背诵。
- **内容判断题**：真实 Jev 输出具有不确定性。练习中给出的分数是教学假设，计算后的规则结果才是确定答案。
- **个人经历题**：只能使用自己实际参与、能够负责的经历。本文的“我负责……”是可调整话术，不能作为个人贡献证明。

### 每天统一评分

每天闭卷过关有 5 道题，每题 4 分，总计 20 分。每题答案列出 4 个得分点，答出一个计 1 分。先录音或写完答案，再对照评分。

- **通过**：至少 16 分，且没有当天标出的关键错误。
- **未通过**：用当天最后 10 分钟重学错题，再做一次不同措辞的口述；仍未通过，次日先安排 20 分钟补考，再学习新内容。
- **最终通过**：七天均通过，并能脱离资料完成第七天的连续追问。

### 本手册的事实边界

本文根据当前仓库实现及已保存验收记录编写，并未在编写时重新执行全部测试。文档中标注“验收记录”的结果，是仓库已有记录，不是本次新测结果。

当前项目具备可恢复扫描、Jev 判断、研究子 Agent、声明证据、持久预算和中文 Web 展示。现有主要证据是离线工程验证；人工质量标签、独立复核和真实付费重复实验尚未完成。不能将模拟结果当真实准确率、成本收益或生产规模证明。

AgentRadar 可以作为自己开发的项目介绍，Pi Durable、Jev 可以作为采用的技术依赖。涉及个人工作时准确说明自己的新增实现；被问到项目起点、已有组件和工作范围时如实回答。本文不修改简历，不要求在每段介绍中重复项目来源。

## 第一天：项目定位、完整流程与架构

### 1. 当天目标与时间安排

今天只建立完整认识，不追求讲清所有恢复细节。

如果看懂流程图却不知道每个方框怎样工作，先读 [跟着一条技术更新学懂 AgentRadar](single-news-walkthrough.md)。第一天只需阅读案例设定、正常路径每步的“第一天先记住”和第一天验收题，将其计入下面的学习时段；详细数据、Outbox、重试和恢复按该文件标注的后续学习日再深入，不要求第一天全部掌握。

- 0～10 分钟：写下自己目前对项目的理解，标出不确定术语。
- 10～60 分钟：学习本日第 2 节，画一轮扫描流程。
- 60～85 分钟：先回答第 3 节问题，再核对答案。
- 85～115 分钟：完成两道练习。
- 115～140 分钟：闭卷完成五道过关题。
- 140～150 分钟：记下最不熟的两个环节。

### 2. 必学知识

**产品定位。** AgentRadar 面向 Agent / 大模型应用开发者，按关注主题和信息源追踪技术更新，筛选值得研究的内容，最终展示有来源证据的中文情报。用户价值是减少查找、重复阅读和核对来源的负担。是否实际节约时间，需要用户或真实实验验证，不能仅凭功能推断。

**一轮扫描。** 触发扫描后，系统受理并保存相关记录；采集到期来源和主题搜索结果；判断相关性与关注价值；关联重复报道、补证或新进展；排序并形成研究计划；研究子 Agent 阅读资料、提交报告与声明；完成 HFS 和证据检查；服务端检查发布条件并写入卡片，最后检查整轮是否存在未处理缺口。阶段图是理解主线，不意味着所有模型与工具调用严格各执行一次。

这里“一轮”指核心业务主流程的一次运行，对应独立 sweep ID，不是只抓一个网页或只调用一次模型。注意：`run_news_sweep` 工具只完成采集、筛选、事件关联与排序；其返回候选后，整轮还要继续研究、证据检查、发布和最终核验。完整主流程、研究证据子流程及恢复/取消图见 [一轮扫描完整流程图](sweep-workflow.md)。

**组件职责。**
- Cron / 手动入口：提供触发，不承担研究分析。
- 主 Agent：在提示与工具约束下协调扫描后的研究、展示和完成等工作。
- 持久扫描任务：执行 gather、gate、dedupe、rank 等有检查点的阶段。
- Pi Agent / Pi Durable 及封装层：提供 Agent、工具调用、持久任务与子 Agent 执行基础。
- Jev：回答结构化判断问题，代码根据判断结果、阈值和规则做业务处置。
- 研究子 Agent：阅读指定条目及相关来源，组织研究、提取声明并提交结果。
- 服务端业务代码：执行状态检查、预算预留、引用验证、唯一发布和终态核验。
- SQLite：保存业务记录与执行记录；业务库与 Durable 执行库有各自职责，不能因都使用 SQLite 就认为天然共享一个事务。
- Vue Web：展示卡片、扫描状态、证据、调用与费用；关闭页面不等于服务端任务停止。

**四个对象。** Sweep 是一轮扫描；item 是一条候选内容；operation 是一次有身份的逻辑判断操作；attempt 是该操作的一次实际尝试。一次扫描包含多个条目，一个判断可能因重试包含多个尝试。研究子 Agent 会话也不是某一次模型请求的同义词。

**为什么采用 Agent。** 搜索与网页阅读需要根据内容组织后续研究，适合工具调用式 Agent；参数检查、状态转移、排序计算、预算和唯一约束适合确定性代码。Agent 的灵活性与代码约束共同构成系统。定时器本身不让一个程序自动成为 Agent。

可选核对：[项目介绍](../README.md)、[演示路线](learning-and-demo.md)、[开发规格的定位与架构](SPEC.md)。SPEC 是设计基线，判断当前完成情况还要结合后续验收记录。

### 3. 每日问题与参考答案

**D1-Q1：项目输入、处理过程、输出分别是什么？**

参考答案：输入包括来源、主题和用户偏好，以及抓取到的技术内容；处理包括采集、判断、事件关联、排序、研究和校验；输出包括中文情报卡片、来源证据以及运行状态。不能只回答“输入提示词，输出回答”，因为它是主动扫描流程。

**D1-Q2：为什么浏览器刷新不会让扫描从头开始？**

参考答案：执行发生在服务端，进度与结果持久化，浏览器只是客户端。刷新后重新获取服务端状态即可。这个结论以服务端仍正常运行为前提；如果服务端退出，还需要其重启恢复机制。

**D1-Q3：Jev 与研究子 Agent 的区别是什么？**

参考答案：Jev 负责限定输入上的结构化判断，例如相关性、事件关系或支持度；研究子 Agent 负责多步读取、整理和生成分析。它们都可能有错误，最终的状态和发布条件由服务端检查。

**D1-Q4：为什么不是一个定时爬虫加摘要就够了？**

参考答案：爬虫和摘要能解决采集与压缩，当前项目还需要事件关联、面向偏好的选择、多来源研究、逐声明证据和长期任务恢复。也不能说普通脚本做不到这些功能；采用 Agent 的理由是研究过程需要根据内容调整工具使用，其余部分仍大量使用普通代码。

**D1-Q5：项目是不是分布式多 Agent 集群？**

参考答案：当前首版定位是单用户、单设备、一个活动扫描，研究子 Agent 是受控的并行研究执行单元。多个子 Agent 不等于跨机器分布式集群，也不能据此宣称高并发生产能力。

### 4. 练习与正确答案

**D1-E1：将角色填入流程。**

题目：手动入口发起扫描；A 执行采集、筛选、事件关联与排序；B 阅读来源形成研究；C 检查引用和发布约束；D 展示结果。A～D 分别是什么？

正确答案：A 是持久扫描任务，其中需要调用 Jev 等服务；B 是研究子 Agent；C 是服务端业务代码，其中语义支持判断需要 Jev；D 是 Web 客户端。主 Agent 协调工具调用，不应把 A～D 全部归为一个模型。

**D1-E2：写一段 60～90 秒介绍。**

合格参考：

> AgentRadar 面向 Agent 和大模型开发者，按配置的来源和主题追踪技术更新。系统先采集、筛选并关联事件，再将排序后的 Top-K 条目交给研究子 Agent，生成带来源证据的中文情报。项目采用 TypeScript、Pi Durable、Jev 和 SQLite。我重点准备讲解的是任务提交与恢复、研究约束和证据发布机制。当前主要完成离线工程验证，真实模型质量与成本收益仍需要进一步评测。

评分时检查：有没有目标用户、完整主线、技术职责、验证边界。个人工作部分按实际参与情况调整。

### 5. 闭卷过关与标准答案

1. **用 60 秒介绍项目。** 得分点：目标用户；技术更新追踪；筛选研究与证据产物；没有虚构效果。
2. **分清四个对象。** 得分点：sweep 是整轮；item 是候选；operation 是逻辑判断；attempt 是实际尝试。
3. **关闭浏览器会怎样？** 得分点：执行在服务端；页面不持有任务生命期；状态持久保存；重新打开获取服务端状态。
4. **为什么同时使用模型与代码？** 得分点：语义判断给模型；研究组织给 Agent；数值和状态约束给代码；模型不能自行跳过硬约束。
5. **描述当前规模边界。** 得分点：单用户；单设备；一个活动扫描；研究子 Agent 不等于分布式集群。

关键错误：把浏览器当执行主体；把所有判断和校验都说成主 Agent 自主完成。

当天交付：流程图、一分钟讲解录音、得分与错题。

## 第二天：分层判断、事件关联、排序与研究协作

研究子 Agent 需要案例化补充时，参阅 [跟着六条新闻学懂研究子 Agent](subagent-mechanism-walkthrough.md)。该专题跨越本手册第二至第六天，不要求第二天一次读完；先完成其委派、会话与工具循环部分。

### 1. 当天目标与安排

0～10 分钟复述第一天流程；10～60 分钟学习判断与研究机制；60～85 分钟问题自答；85～115 分钟完成计算与关系练习；115～140 分钟过关；140～150 分钟纠错。

### 2. 必学知识

**六类判断。** relevance 判断与关注主题的相关性；worth-attention 判断是否值得关注并给出新颖性信息；same-story 判断与已有事件的关系；importance 判断对当前读者的重要性；hfs 从 Hype、Facts、Signal 三个维度评分；claim-support 判断给定证据对具体声明的支持、充分性和冲突情况。六类命令不等于每条信息都恰好调用六次。

**HFS 的含义。** Hype 关注宣传、夸张等成分；Facts 关注文本呈现的来源与可检查细节；Signal 关注对工程实践的可行动价值。三维可以同时有较高分，并非概率之和为 1 的互斥分类。Facts 高也不等于事实已经被人工核实。

**先召回，再判关系。** 系统先用文本特征寻找可能相关的历史条目，当前包括 Unicode 规范化、英文实体/版本 token 和中文双字片段，再由 Jev 判断。候选最多 12 个，已知日期用于收缩范围。候选召回不是语义结论；历史代表未进入候选时，后续判断再好也可能漏检。当前这里不是 BGE 向量检索，也不是简历中另一个混合检索项目。

**事件关系。** 当前策略区分 different、duplicate、evidence、development、uncertain。same-story 不只是一个“是否相同”的布尔值，还判断发展、已有覆盖、信息增量和材料充分性。只有明确覆盖且没有新发展与补充时才保守抑制为 duplicate；不确定不应直接删除。

**排序公式。** 当前 rankScore = importance × topicWeight × sourceWeight × freshness。importance 已经接收部分主题与来源背景，代码仍显式乘权重；这是一项当前设计，应通过评测检验是否存在过强加权，不要宣称它是唯一最优公式。新鲜度在 24 小时内为 1，超过 24 至 72 小时为 0.85，超过 72 至 168 小时为 0.7，其后为 0.55。无日期按 48 小时档处理。练习使用本轮冻结的参考时间。

**研究计划。** 默认研究条目上限 6，研究并发上限 2；工具每次最多两个批次，每批最多四个 item。四个 item 是一个批次的容量，不是四个同时运行的子 Agent。单轮计划和工具参数同时约束实际调用，并非两个批次一定能研究 8 条。子 Agent 只应研究已选择计划中的条目。

**取舍。** Top-K 可以限制深度研究工作量，但可能漏掉被筛选或排序压低的重要条目。Jev 是否比其他方案更便宜、更快、更准确，需要真实对照；当前只能说明职责划分和控制方式。

可选核对：[事件策略](../apps/dna-server-api/src/news/story-policy.ts)、[排序](../apps/dna-server-api/src/news/rank.ts)、[研究工具](../apps/dna-server-api/src/agents/tools/research-items.ts)、[HFS 命令](../apps/dna-server-api/prompt_engineering/jev/hfs/command.json)。

### 3. 每日问题与参考答案

**D2-Q1：为什么不让一个大模型研究全部内容？**

参考答案：可以这样做，并适合作为全量基线；当前采用先判断再研究，目的是把研究预算集中到更有价值的条目，方便记录与诊断各阶段。代价是前置误筛会造成漏检，需要以质量与成本联合评价，不能只看调用变少。

**D2-Q2：同 URL 去重和同事件去重有什么不同？**

参考答案：同 URL 是条目身份层面的问题；同一事件可能有多个 URL，需要语义关系判断。即使属于同事件，也可能是补证或后续进展，不都应压成重复。

**D2-Q3：Jev 输出高置信值就能直接采取动作吗？**

参考答案：需要先确认问题与输入，再读取对应判断值并应用策略；不能把一个笼统 confidence 当成所有业务动作的阈值。当前事件与证据策略会综合多个判断，保留不确定分支。模型值也没有在本项目中被证明是事实真实概率。

**D2-Q4：为什么限制并发还要限制研究条目总数？**

参考答案：并发控制同时在途的工作，条目总数控制整轮总工作量。只限并发，任务仍可能长时间持续研究大量条目；只限总量，同时启动过多请求仍可能触发限流或资源压力。

**D2-Q5：主题权重调高后，是不是所有旧扫描立即按新权重重排？**

参考答案：已有扫描使用受理时冻结的上下文，新偏好影响新扫描。这样避免恢复时同一轮混用两套策略。它是可解释一致性选择，不意味着旧卡片永远无法另行重新计算。

### 4. 练习与正确答案

**D2-E1：计算排序。** 假设三条均通过前置检查，K=2。

- A：importance=0.8，主题权重=1.5，来源权重=1，20 小时前发布。
- B：importance=0.9，主题权重=1，来源权重=1，48 小时前发布。
- C：importance=0.7，主题权重=1.2，来源权重=1.1，10 小时前发布。

正确答案：A=1.2；B=0.765；C=0.924。顺序 A、C、B，研究 A 与 C。乘权重后的排序值允许大于 1，不能把它叫作概率。题目没有同分，不需要讨论同分排序。

**D2-E2：按规则判断事件关系。** 教学假设：same≥0.85、sufficient≥0.8 才进入明确关系判断，yes≥0.85，no≤0.2。

- A：same=.95，sufficient=.9，development=.1，covered=.95，addition=.1。
- B：same=.95，sufficient=.9，development=.95，covered=.1，addition=.1。
- C：same=.95，sufficient=.9，development=.1，covered=.1，addition=.95。
- D：same=.6，sufficient=.9，development=.1，covered=.95，addition=.1。

正确答案：A duplicate；B development；C evidence；D uncertain。D 即使 covered 较高，也不能越过 same 的不确定性直接判重复。这些分数是练习输入，不是真实模型预测。

### 5. 闭卷过关与标准答案

1. **说出六类判断。** 得分点：相关性与关注价值；事件关系；重要性与 HFS；声明支持度，并说明各自用途。
2. **如何处理同事件多篇报道？** 得分点：先召回；再判断；区分重复/补证/进展；不确定不能一律删除。
3. **解释排序。** 得分点：importance；主题权重；来源权重；新鲜度，并正确描述乘法组合。
4. **区分 K、批次与并发。** 得分点：K 控制条目计划；批次可含多个条目；并发控制同时运行的研究单元；默认上限与工具单批容量不能混淆。
5. **分层研究有什么代价？** 得分点：限制研究工作量；前置错误会漏检；需要全量与等 K 对照；没有真实数据不能声称已节省某百分比。

关键错误：将排序值当概率；将不同版本必然视为重复；声称每条新闻启动一个子 Agent。

当天交付：六类判断笔记、两道练习结果、两分钟设计取舍录音。

## 第三天：持久执行、崩溃恢复、上下文与缓存

### 1. 当天目标与安排

0～10 分钟复习判断与研究；10～60 分钟学习恢复与一致性；60～85 分钟自答；85～115 分钟完成崩溃练习；115～140 分钟过关；140～150 分钟纠错。

### 2. 必学知识

**持久执行。** 普通内存程序在进程退出后丢失局部变量和等待状态。Durable 执行保存任务状态与检查点，重新启动后继续推进。当前扫描检查点包括 gather、gate、dedupe、rank，以及保存恢复位置和下次唤醒时间的 retry。业务库同时保存来源状态、条目处置和判断结果。恢复需要两类记录协作，并不只是保存聊天历史。

**阶段重放与操作复用。** 一个阶段可能因为崩溃再次进入，已经成功落库的逻辑判断可以复用，避免对每个条目从零开始。是否能跳过一次外部调用，取决于是否有足够的成功记录与身份信息，而非“执行过”这一主观推断。

**不确定窗口。** 外部服务执行成功与本地数据库确认成功不是一个原子事务。请求已返回、结果落库前崩溃时，本地不能可靠确认其完成，重试可能重复执行和计费。unknown 是未知，不是成功、失败或免费。当前记录和预算机制用于限制、追踪这种不确定性，不能消除供应商侧全部重复。

**上下文冻结。** 扫描受理时保存本轮 referenceTime、偏好、来源、策略、命令、提示、模型配置、预算等。恢复时继续使用原上下文，避免本轮前半段按旧偏好筛选、后半段按新偏好排序。referenceTime 固定让新鲜度与时间窗口不因重启时间变化而随意漂移。保存请求模型名不等于冻结供应商实际模型权重；尚未首次获取的网页也可能更新，不能承诺整个世界的确定性重放。

**两类快照。** 上下文快照保存“本轮怎么做”；来源正文快照保存“本轮读到了什么”。二者不同，不能相互替代。配置快照使用白名单，不能把带密钥的完整配置对象直接写入审计数据。

**缓存身份。** 同一次 operation 成功后的复用，与精确判断缓存相关但不等同。精确缓存包含规范化输入、上下文与命令/模型等身份信息。规范化只排序对象键，保留文本和数组顺序。标题相同不代表证据相同；证据变化后的 HFS 或 claim-support 不能直接复用旧判断。上下文含 referenceTime，因此新的扫描通常不应被假设会广泛跨轮命中缓存。命中也需要本轮记录与来源引用，不能抹去审计关系。

可选核对：[上下文](../apps/dna-server-api/src/news/context.ts)、[判断操作](../apps/dna-server-api/src/news/operations.ts)、[M2 完整验收](m2-verification.md)。历史第一批文档里的剩余工作，不能直接当作当前仍未实现。

### 3. 每日问题与参考答案

**D3-Q1：持久执行与普通日志有什么区别？**

参考答案：日志主要帮助人理解发生了什么；恢复机制需要机器能读取的任务身份、状态、检查点与可复用结果，并据此决定下一步。不能仅凭“日志里看到执行成功”就安全地驱动恢复。

**D3-Q2：阶段已经执行了一半，重启后会不会重复进入？**

参考答案：可能。检查点没推进时会重新进入该阶段，但条目与操作级成功记录能减少重复工作。阶段重入和所有外部调用重做不是一回事。

**D3-Q3：为什么不直接使用最新配置恢复？**

参考答案：会导致同一扫描混用策略，改变候选、排序和支持度解释。当前保留受理时上下文，新偏好用于新扫描。明确发起重算是另一项业务动作。

**D3-Q4：缓存会不会掩盖模型错误？**

参考答案：缓存只复用已确认的结果，不能提高该结果本身的语义正确率。因此要绑定输入与版本，不缓存失败或非法响应，并在策略、输入变化后避免错误复用。模型质量仍需独立评测。

**D3-Q5：有快照是不是完全可重现？**

参考答案：快照提高输入与决策过程的可追溯性，不能保证真实供应商输出完全一致；模型别名可能变化，首次网页抓取也有时效差异。应说固定已保存材料与上下文，不说端到端绝对确定。

### 4. 练习与正确答案

**D3-E1：分析三个崩溃位置。**

- A：阶段检查点未推进，但某条 Jev operation 已成功落库。
- B：供应商返回后、本地成功记录落库前退出。
- C：处于 retry 等待，未来唤醒时间已保存，进程重启时尚未到期。

正确答案：A 可能重入阶段，但复用该 operation 成功结果；B 不能臆断完成，保留不确定尝试并在允许重试时可能再次出站，预算仍约束；C 应遵守持久等待时间，不能因为重启就立即进行无间隔重试。B 的确切后续还受重试分类、截止和预算限制，并非一律重试。

**D3-E2：判断能否直接复用旧结果。**

- A：原 operation 已确认成功，同一恢复上下文、同一输入。
- B：标题不变，但研究报告增加了新证据。
- C：策略版本改变，并发起了新扫描。
- D：供应商失败，本地只有一条错误记录。

正确答案：A 可以复用已有成功操作；B 不能仅凭标题复用，需按材料版本形成判断身份；C 不能沿用旧身份命中，应使用新上下文和策略；D 不能作为成功结果复用。新的精确 key 是否命中，以完整身份计算为准。

### 5. 闭卷过关与标准答案

1. **恢复依赖哪些记录？** 得分点：任务检查点；业务条目状态；成功操作结果；等待和重试信息。
2. **解释未知窗口。** 得分点：外部与本地不是同一事务；本地未确认；可能再次执行；不能保证不重复计费。
3. **解释上下文冻结。** 得分点：受理时保存；恢复用原配置；新偏好影响新扫描；不包含密钥等完整敏感配置。
4. **为什么缓存不能只用标题？** 得分点：正文可能变化；证据可能变化；命令/策略/模型影响结果；需要完整输入与上下文身份。
5. **配置快照和正文快照有什么不同？** 得分点：前者记录执行规则；后者记录读取材料；两者都支持追溯；都不能保证模型输出完全确定。

关键错误：声称任何崩溃都不重复请求；把 unknown 当免费；声称模型别名等于固定模型权重。

## 第四天：提交对账、幂等、租约与取消隔离

### 1. 当天目标与安排

0～10 分钟复述未知窗口；10～60 分钟学习下面三个机制；60～85 分钟自答；85～115 分钟画时序并做取消练习；115～140 分钟过关；140～150 分钟纠错。

### 2. 必学知识

**问题一：双库提交缺口。** 业务库保存扫描、上下文和提交意图，执行库接纳 Durable 提交。二者没有共享原子事务。直接先写业务后提交执行系统，会在两步之间崩溃，留下无人执行的扫描；先提交再保存业务，则可能执行开始而业务关联缺失。简单交换顺序不能消除所有窗口。

**当前方案：事务 Outbox 与对账。** 受理时，在业务库同一事务保存扫描、冻结上下文和完整提交草稿。后台取出待处理意图，用保存的 requestId 和 payload 向同一 Durable 会话提交，取得回执后补写关联。启动时与周期性对账处理未完成意图。

用一个虚构 ID 串起来：业务扫描 sweep=42，requestId=R42。第一次提交时 Durable 已接纳为 submission=900，但关联尚未写回便崩溃。恢复后仍提交 R42 与原草稿，在 SDK 幂等受理语义下取得原 submission，再把 900 关联给 42。重新生成 R43 会把恢复变成另一次新提交，不能这样补偿。

**租约与 fencing。** 租约让某个对账处理者临时占有本地记录，避免多人同时随意关联；过期后允许接管。leaseToken 相当于这次占有的凭证，旧持有者迟到后不能覆盖新持有者的关联。租约过期不代表执行系统没有接纳，所以接管仍必须复用原 requestId。租约解决本地归属，requestId 解决提交身份，二者职责不同。

**幂等的三个层次。** 同一次受理请求重试，使用稳定请求身份；同条目新闻卡片重复写入，用数据库级唯一约束兜底；不同条目属于同事件，依赖候选召回与语义关系判断。唯一索引不是“新闻世界的全局语义去重器”。也不能将 SDK 幂等受理扩展为所有外部服务都 exactly-once。

**问题二：取消后迟到结果。** 单纯设置页面状态为取消不够。当前取消先在业务库使旧执行失效，增加 execution_epoch，标记相关待执行记录，再尝试中止 Durable 任务。研究子任务持有创建时绑定的 sweepId、epoch、item 集合和 deadline，不得临时改绑到新一轮。

例如旧任务持有 epoch=3，取消后业务记录变为 epoch=4。旧任务返回时，受保护的业务写入和新预算预留检查发现版本不符，应拒绝。当前状态不允许写入或超过截止，也会触发隔离。epoch 不是缓存版本，也不是重试次数。

**取消边界。** 本地可以拒绝旧结果进入业务状态，但不能保证供应商立即停算或免除费用。已经发生请求的迟到费用结算可以保留作审计，不能把“拒绝业务写入”说成“拒绝一切数据库记录”。用户取消的正常终态为 cancelled；因截止等原因终止时可能根据已有可用结果呈现 partial 或 failed。

**问题三：超时不是结束。** 本地 Promise 超时只代表调用者不再等待；底层请求可能还在运行。如果立即释放槽位再启动新研究，真实在途工作可能超出限制。当前容量控制持有槽位直到真实研究结束。若进程退出，内存信号量不能宣称跨机器继续存在，恢复另由持久任务与业务约束处理。

可选核对：[Outbox 仓库](../apps/dna-server-api/src/db/repos/submissions.ts)、[对账](../apps/dna-server-api/src/news/submissions.ts)、[取消流程](../apps/dna-server-api/src/news/lifecycle.ts)、[执行校验](../apps/dna-server-api/src/db/execution.ts)、[研究容量](../apps/dna-server-api/src/news/research-capacity.ts)。

### 3. 每日问题与参考答案

**D4-Q1：为什么不用一个数据库事务包住一切？**

参考答案：当前业务库与执行库属于不同持久边界，不能用业务库本地事务原子覆盖 SDK 接纳和外部请求。Outbox 使本地受理意图可靠，再依赖稳定身份与对账最终补齐。不能只说“事务太慢”。

**D4-Q2：为什么要保存完整提交内容？**

参考答案：恢复时应重交原来的请求，而非用当前提示词或配置重新生成一个内容不同的请求。稳定 ID 和稳定内容共同让对账具有可解释的身份；上下文冻结也避免恢复期间配置漂移。

**D4-Q3：SDK 已经有 requestId，为什么还要 Outbox？**

参考答案：SDK 幂等解决同一提交重复接纳，但不知道业务库有哪些提交意图尚未送达。Outbox 让应用知道要补交什么，并补写业务关联。只有 requestId 不能让丢失在提交前的工作自动出现。

**D4-Q4：有唯一索引，为什么还讨论幂等逻辑？**

参考答案：唯一索引是并发下最后的约束，业务仍需要稳定身份、冲突处理和正确返回已有结果。先查询不存在再插入会有竞争窗口，数据库唯一约束仍有必要；它也不覆盖外部付费调用的副作用。

**D4-Q5：为什么先 fencing 再 abort？**

参考答案：abort 可能延迟或失败。先持久使旧执行失效，后续返回就不能继续推进业务；再中止任务以减少无用工作。顺序反过来会让中止期间的迟到结果仍有机会写入。

**D4-Q6：旧任务只是超时，能直接让新任务占用其槽位吗？**

参考答案：不能仅因调用者超时就认定真实工作结束。当前持有真实在途容量直到研究结束，避免多次工具调用叠加扩大实际并发。等待受截止与取消约束，不是无限等待承诺。

### 4. 练习与正确答案

**D4-E1：依次解释三个提交窗口。**

- A：业务事务提交后，尚未调用 SDK 就退出。
- B：SDK 已接纳，尚未本地关联就退出。
- C：本地已关联，旧对账处理者又迟到返回。

正确答案：A 从 Outbox 找到原意图并提交；B 使用原 ID、原内容、同会话再次提交，取得原受理结果后关联；C 依据状态、leaseToken 与当前执行版本进行条件更新，旧归属不能覆盖新记录。关联时也不能把已完成任务错误改回运行中。A/B 不应新建另一个业务扫描冒充恢复。

**D4-E2：分析取消后的四个动作。** 旧研究持有 epoch=7；用户取消后业务 epoch=8。

- A：旧研究尝试提交报告。
- B：旧研究尝试预约下一次模型请求。
- C：已发送请求返回实际 usage，补充费用审计。
- D：页面显示取消成功，所以断言供应商账单为零。

正确答案：A 应拒绝旧版本业务写入；B 应拒绝新预约；C 可以保留已经发生请求的审计结算，但不能推进已取消扫描；D 错误，用户取消不证明外部未执行或未收费。

### 5. 闭卷过关与标准答案

1. **复述接纳后崩溃恢复。** 得分点：业务意图仍在；同会话复用原 requestId/payload；取得已有受理结果；补关联而非新建工作。
2. **区分 requestId 与租约。** 得分点：前者是提交身份；后者是本地处理归属；过期允许接管；接管不意味着可以换请求 ID。
3. **区分三类重复。** 得分点：重复受理；同 item 发卡唯一；同事件关系判断；不能将任一层说成全链路 exactly-once。
4. **解释 epoch。** 得分点：原执行绑定旧版本；取消持久增加版本；业务写入/预约验证；迟到费用审计不等于业务继续。
5. **解释超时与容量。** 得分点：调用者超时；底层仍可能执行；槽位持有至真实结束；避免实际在途数膨胀。

关键错误：租约到期就换 requestId；取消等于供应商立即停算；声称数据库唯一约束避免所有模型重复计费。

当天交付：提交时序图、取消场景答案、三分钟难点讲解。

<a id="day-5"></a>

## 第五天：来源快照、逐声明证据与发布检查

### 1. 当天目标与安排

0～10 分钟复习提交与取消；10～60 分钟学习证据机制；60～85 分钟自答；85～115 分钟完成引用和状态练习；115～140 分钟过关；140～150 分钟纠错。

### 2. 必学知识

**证据链。** 一张卡片不是只有一段总结和几个 URL。研究报告提出 claims，每条 claim 关联一个或多个引用；引用指向保存的 source snapshot，包含正文 hash、原文 quote 与字符区间。来源快照保留 URL、实际获取时间、正文和截断标记，本轮 URL 与快照绑定后不被新抓取原地覆盖。

**为什么保存正文。** URL 指向的网页会更新或消失，同一 URL 不等于同一正文。保存快照让人知道本轮究竟读到了什么；保存获取时间，不应冒充网页首次发布时间。正文经过 NFC 和 LF 规范化，区间针对保存后的正文，而不是原始 HTML 或显示排版。

**确定性校验。** 当前检查快照属于本轮、来源在允许的 URL 内、引用非空且不超长、位置合法、正文切片等于 quote、正文 hash 一致。未给位置且同一引用出现多次时，不应猜测唯一位置。位置使用 JavaScript 字符串 UTF-16 单元，不能一概叫 Unicode 字符数或 UTF-8 字节偏移。

**语义判断。** 引用匹配后，将声明与引用及周边上下文交给 claim-support。当前策略依次处理冲突、充分性、支持度：有多个不同来源 URL 且冲突值达门槛时为 conflicting；材料不充分为 insufficient；充分且支持度达门槛为 supported；充分且支持度很低为 unsupported；中间不确定区域为 insufficient。不同 URL 也不自动证明来源独立。

当前默认阈值：conflicting≥0.8，sufficient≥0.8，supported≥0.7，unsupported≤0.2。有效引用对应的正文被截断时，保守不能作为 supported；没有有效引用也不能。数字无需作为面试重点背诵，理解分支含义更重要。

**三层保证。** 引用匹配证明保存的文本存在；来源支持度评价文本与声明的关系；事实真实性还涉及来源本身是否可靠。不能把 supported、Facts 高分或多个链接叫作已经证明真实。

**发布检查。** 服务端不接受 Agent 自填的 verifiedClaims 作为真值，而是重新读取本轮成功判断与有效快照，核对 hash 与区间，生成可展示的已支持声明。当前版本化扫描的发布条件还包括条目在研究计划、研究报告完成、HFS 存在、至少有有效支持声明等。至少一条支持声明不代表卡片中每一句分析都被逐句证明，分析与已核验声明应区分。

**整轮完成检查。** 发布一个卡片与整轮完成是两件事。finalization 检查来源、条目处置、判断操作、研究状态、预算缺口等；发现缺口可进行有限修复。没有缺口且有卡片为 completed，没有缺口且无卡片为 no_news；缺口无法修复时，依据已有可用结果区分 partial 与 failed。不能因为“零卡片”就直接标 no_news，也不能因为“有卡片”就自动标整轮成功。

可选核对：[快照校验](../apps/dna-server-api/src/news/snapshots.ts)、[声明评估](../apps/dna-server-api/src/news/evidence.ts)、[完成检查](../apps/dna-server-api/src/news/finalization.ts)、[M3 展示验收](m3-verification.md)。

### 3. 每日问题与参考答案

**D5-Q1：hash 能防止内容造假吗？**

参考答案：hash 可检查保存后的内容是否与记录一致，不能判断最初抓取内容是否真实。若来源本身错误，一致的 hash 也不能使它变正确。它提供内容身份和一致性检查，不是事实裁判。

**D5-Q2：为什么引用正确，但仍可能不支持结论？**

参考答案：可能断章取义、忽略否定词、把计划写成已完成、将局部实验推广到所有场景。确定性匹配只检查文本是否存在，语义支持需要结合声明和上下文判断。

**D5-Q3：为什么材料不足与明确不支持要分开？**

参考答案：前者缺少判断依据，补充资料可能改变结果；后者是在足够材料下发现声明缺乏支持或与材料不符。混为一类会损害排障和研究方向，也会把未知伪装为否定。

**D5-Q4：为什么不直接相信子 Agent 返回的 supported=true？**

参考答案：Agent 可能引用不存在材料、错误复制 ID 或越过检查。服务端需要重新绑定本轮快照和成功判断，把模型输出作为待验证输入而非授权凭证。

**D5-Q5：一轮扫描没有卡片，一定失败吗？**

参考答案：不一定。所有来源和条目都得到合理处置、没有未完成缺口时可以 no_news；如果因抓取、研究或预算失败造成无卡片，则应保留失败或部分完成信息。终态按整轮检查决定。

### 4. 练习与正确答案

**D5-E1：检查引用区间。** 假设保存正文为 `Version 2 is planned.`，只有 ASCII 字符，区间使用从 0 开始、左闭右开。

- A：quote=`planned`，start=13，end=20，hash 正确。
- B：quote=`released`，start=13，end=20，hash 正确。
- C：A 的引用匹配，但声明是“版本 2 已经发布”。

正确答案：A 正文切片等于 planned，区间检查通过；B 切片不等于 released，拒绝；C 引用存在仍不支持“已经发布”，不能通过引用匹配直接将声明认定 supported。具体模型是否误判不能保证，但服务端不应把字符串匹配等同语义支持。

**D5-E2：按当前证据策略判断。** 除特别注明外，均有有效、未截断且属于本轮的引用。

- A：supported=.9，sufficient=.9，conflicting=.1。
- B：supported=.9，sufficient=.5，conflicting=.1。
- C：supported=.1，sufficient=.9，conflicting=.1。
- D：supported=.9，sufficient=.9，conflicting=.9，有两个不同来源 URL。
- E：与 D 相同，但只有一个来源 URL。
- F：supported=.9，但正文被截断。

正确答案：A supported；B insufficient；C unsupported；D conflicting；E insufficient；F insufficient，不应因 supported 分值高而跳过正文完整性检查。D 的多 URL 是当前冲突规则条件，不表示已经验证来源相互独立。

### 5. 闭卷过关与标准答案

1. **描述完整证据链。** 得分点：claim；quote；snapshot/hash；本轮绑定与区间。
2. **引用匹配保证什么？** 得分点：文本存在；位置匹配；内容一致；不能证明语义支持或客观真实。
3. **区分四种状态。** 得分点：支持；充分材料下不支持；材料不足；来源冲突。
4. **为什么发布时重新检查？** 得分点：不信任自报核验；绑定本轮判断；重核快照与引用；有服务端发布条件。
5. **区分终态。** 得分点：completed 有卡片且无缺口；no_news 无卡片且无缺口；partial 有缺口但有可用结果；failed 有缺口且无可用结果，本题指常规完成核验路径。

关键错误：hash 证明来源真实；Facts 分数等于事实正确率；零卡片一律 no_news。

当天交付：引用练习、六个状态答案、两分钟证据链讲解。

## 第六天：持久预算、异常处理、观测与评测

### 1. 当天目标与安排

### 2. 必学知识

**请求前预留。** 在数据库事务中检查已用请求数量并写入预约，成功预约后再出站。若先请求再计数，多个并发调用可能同时认为有余额，也可能请求完成后崩溃导致漏记。事务预约把并发竞争和重启后的计数放到持久边界内。

**失败与未知也消耗尝试。** 外部是否收费不能仅看本地成功与否。当前重试与 unknown attempt 都占用请求计数，不因超时自动退还。成功缓存命中不发生新出站，不预约新的外部请求，但保留缓存来源与历史费用引用。

**预算种类。** 当前默认研究项上限 6、研究并发 2、每条研究项模型调用上限 12、每次请求输出上限 2,000 tokens；Jev 请求上限 800 等是工程配置，不是实际消耗或性能成果。批次模型请求同时计入该批各 item 的调用额度。单独交互式深度研究属于不同入口，不能把扫描预算描述成整个应用所有交互的统一无限范围保证。

**请求硬计数与金额软边界。** 数据库可明确拒绝超过请求数的新预约。金额只有在用量和价格信息完整时才能准确估计；当前已记录金额达到告警值也会拒绝后续预约，但已有在途请求仍会增加费用，unknown 金额无法被准确计入，所以不能保证实付账单绝不越线。输出 token 上限也依赖供应商遵守请求参数。

**费用分类。** reported 是供应商或返回元数据报告的金额，不自动等于已对账实付账单；estimated 是按用量与价格估算；unknown 是无法确定；mock 是模拟费用；not_applicable 用于不适用的记录。已知零与未知不同。费用覆盖率表达有费用信息的尝试比例，不等于正确率或节省率。缓存引用不再次算作新账单。

**错误与重试。** 当前判断请求通常对 429、5xx 和部分网络异常有界重试；参数模板/校验问题、鉴权/余额/不可用等明确错误不应无意义重试。持久保存 retry_at，并受次数与整轮截止约束。不要把所有工具都概括成同一个重试次数。Jev operation 当前一般最多四次尝试，非法响应的重试更保守，最多两次尝试；阶段退避和底层 operation 是不同层次。429 后退避也不意味着保证下一次成功。

**排障顺序。** 先确认 sweep 身份和终态，再看阶段、last_progress、wait_reason、next_wake；然后定位受影响 item、operation 与 attempt；查看原始错误、预算拒绝、研究状态；最后看 publication/finalization gaps。不要看到没有新日志就认定卡死：可能在合法重试等待、研究仍在途或尚未到下次唤醒。

**工程测试与模型评测。** SIGKILL 测试验证进程退出后的恢复行为；fixture 模拟模型与资料，验证业务链和约束，不证明真实模型语义正确率。真实模型质量需要来源数据、人工标签与复核。已有 180 份真实公开技术资料池和 160 条合成工程候选是两套数据；真实来源不等于已经有人工 gold 标签。

**A/B/C 对照。** A 对日期等输入资格合格的全部输入研究，显式扩大预算；B 经判断与事件关联后研究 Top-K；C 按时间取相同 K 研究。固定来源快照、研究配置和下游验证，隔离数据库与冷缓存。B/C 比较同等研究数量下的选择价值，A/B 比较全量与分层的质量/工作量取舍。若 B 合格不足 K，不强行补入被拒条目。

**数据与指标。** 同一事件的翻译、转载和相邻版本应保守放在同一 split，避免开发与测试泄漏。dev 用于调试；test 冻结后不根据结果回调参数。门控召回衡量有价值样本是否保留，Top-K 精度衡量选出的内容有多少有价值；技术失败不能通过删除分母美化指标。重复实验不能把同一批样本算作新增独立样本。真实质量、成本节省与生产 P95 尚不能由当前 fixture 成绩推导。

可选核对：[预算实现](../apps/dna-server-api/src/news/budgets.ts)、[M2 验收](m2-verification.md)、[M4 工程记录](m4-verification.md)、[评测流程](../evaluation/README.md)、[真实资料说明](public-data-and-learning-verification.md)。

### 3. 每日问题与参考答案

**D6-Q1：失败请求为什么也占额度？**

参考答案：请求可能已经到达供应商并消耗资源，本地失败不证明未执行。保守计入尝试可避免通过反复超时无限发请求，也防止重启后丢失消耗记录。

**D6-Q2：配置一美元告警是否保证花费不超过一美元？**

参考答案：不能。当前在已知记录达到告警后可阻止新预约，但在途请求、价格估算误差和未知费用可能使实付超出。它是基于当前可见费用的软金额边界，请求数量才有明确硬计数。

**D6-Q3：200 个测试都通过，能说准确率很高吗？**

参考答案：不能。测试可能是工程场景和模拟输出，证明受测行为符合断言，不构成真实输入上的标注质量评测。需要区分恢复正确、业务约束正确与语义判断正确。

**D6-Q4：为什么 C 组必须与 B 组使用相同 K？**

参考答案：控制研究数量，避免 B 只是因为研究更多而表现更好。两组采用相同研究与校验链，差异集中在选择策略。若实际合格数量不同，需要报告实际数量，不能隐藏。

**D6-Q5：怎么回答“成本降低多少”？**

参考答案：目前实现了限制研究项、缓存复用与持久预算，但真实对照和账单核验尚未完成，因此不能给出节省比例。后续会在相同数据、研究配置和质量条件下同时比较成本、漏检和产出质量。

**D6-Q6：系统显示一直 running，应该怎么办？**

参考答案：先看是否在合法等待、下次唤醒是否未到，再检查真实进展时间、在途研究、重试错误与预算拒绝，最后看完成缺口。不能直接点击多次新建扫描，也不能把页面状态当全部事实。

### 4. 练习与正确答案

**D6-E1：最后一个额度的竞争。** 上限 10，已预约 9，两请求同时尝试事务预约；成功预约的请求随后超时，无法确定外部执行情况。

正确答案：在事务检查与预约约束下，只有一个能占用最后额度，另一个被拒绝；总预约数为 10。超时未知尝试不自动退回，因此重启后也不能再获得第 11 次额度。这里讨论的是当前作用域内该种请求上限，不是整个应用所有请求。

**D6-E2：计算质量指标并解释。** 教学数据：人工有价值样本 40 条；门控保留其中 32 条；最终 K=6 中有 5 条人工判定有价值；另有技术错误，原有分母不变。

正确答案：门控召回=32/40=80%；Top-K 精度=5/6≈83.3%。不能计算真实成本节省，因为未提供实际成本；也不能用 Top-K 精度替代门控召回。六个选中样本很少，应报告分母和不确定性，不能直接宣称已达到稳定生产质量。若技术错误影响预测，应按预先定义口径计入，不得事后删除。

**D6-E3：费用的正确表述。** 假设 10 次实际尝试：6 次 reported、2 次 estimated、2 次 unknown；已知类别合计 0.08 美元。

正确答案：金额信息覆盖率为 8/10=80%；可报告已知 reported 与 estimated 的合计为 0.08 美元，但应分别展示其构成，本题未给各自金额，不得虚构拆分；另有 2 次费用未知。不能说总账单恰好 0.08 美元，也不能说余下两次免费。

### 5. 闭卷过关与标准答案

1. **解释请求前预约。** 得分点：事务检查；持久计数；并发防超发；重启不清零。
2. **区分请求上限与金额告警。** 得分点：硬请求计数；已知费用影响后续预约；在途和未知金额；不能保证实付绝不超线。
3. **解释重试策略。** 得分点：按错误分类；有界次数；持久等待与截止；失败不当否定答案。
4. **解释 A/B/C。** 得分点：A 全量；B 分层 Top-K；C 时间同 K；其他研究与校验条件固定。
5. **当前效果如何准确表达？** 得分点：工程验证有记录；fixture 非真实质量；标签/复核/真实实验待完成；无准确率或节省率承诺。

关键错误：unknown 当零；模拟零费用当成本收益；测试通过数当准确率；声称一美元告警保证账单最多一美元。

### 3. 每日问题与完整参考答案

**D7-Q1：请用一分钟介绍项目。**

参考稿：

> AgentRadar 是面向 Agent 和大模型开发者的主动技术情报助手。用户配置关注主题和来源后，系统定时采集技术更新，先做相关性筛选、事件关联和重要性排序，再将 Top-K 条目交给研究子 Agent，生成附带来源证据的中文卡片。技术上采用 TypeScript、Pi Durable、Jev 和 SQLite。项目重点补齐了提交对账、恢复隔离、证据发布约束和持久预算，不仅展示结果，也保留判断、引用和调用记录。目前主要完成离线工程验证，真实模型质量与成本收益还需要进一步实验。

答案重点：产品先于术语；实际工作先于泛泛架构；验证情况说清，不用无依据指标填充。

**D7-Q2：请用三分钟详细介绍项目。**

参考稿：

> AgentRadar 面向 Agent 和大模型开发者，解决持续追踪技术更新时来源分散、重复报道多、需要核对原文的问题。系统按配置主动扫描，将筛选后的内容组织成中文情报卡片，并展示原文引用和执行过程。
>
> 一轮处理先采集到期来源和主题搜索结果，利用 Jev 判断相关性、事件关系与重要性，再结合主题、来源权重和新鲜度形成研究计划。研究子 Agent 负责读取资料、整理结论与声明；服务端负责预算、状态和发布条件检查。Pi Durable 提供持久任务基础，SQLite 保存相关记录。
>
> 一个关键设计是提交对账。业务库保存扫描，并不代表执行系统已经收到；执行系统接纳后，也可能在本地写回关联前崩溃。因此受理时把提交意图和业务记录放在同一事务，对账程序使用保存的 requestId 与原提交内容补交，重启后补齐关联。已落库的成功结果可以复用，但供应商完成、本地未确认的请求仍可能重试和重复计费。
>
> 另一个设计是证据约束。研究声明关联保存的来源正文、哈希、引用和字符区间。先检查引用是否确实存在，再判断来源能否支持声明；发布时由服务端重新读取有效记录。这里保证的是可追溯和来源支持检查，不能把模型分值当事实真实概率。
>
> 项目还通过执行版本隔离取消后的迟到写入，通过持久预算和并发限制约束研究。已有离线验收覆盖关键位置的进程终止、恢复和发布约束。下一步需要完成人工标注、独立复核与真实模型对照，联合评价质量、成本和耗时。

讲到个人负责时，只保留自己做过的工作。若面试官提前追问，应停下展开，不强行念完介绍。

**D7-Q3：你遇到的最难问题是什么？**

参考答案，以提交对账为例：

> 难点是业务状态和执行受理不在同一个事务里。最容易忽略的是执行系统已经接纳，但业务库没有收到或保存回执。直接重新创建请求可能重复执行，不重试又可能留下永远不运行的扫描。我使用事务 Outbox 保存原提交意图，再以固定 requestId 做启动和周期对账，使用租约控制本地关联归属。验收记录包含接纳后终止进程、再启动关联原任务的场景。这个方案解决提交与关联缺口，不承诺所有外部请求只执行一次。

若没有亲自处理该问题，改为“项目中我重点理解和验证的难点”，并选择自己的真实难点叙述，不虚构调试经历。

**D7-Q4：为什么选 SQLite，不用 Redis、消息队列或 PostgreSQL？**

参考答案：

> 当前定位是单用户、单设备和一个活动扫描，SQLite 支持本地事务、持久化和唯一约束，部署依赖少，也符合 Durable 执行基础的使用方式。当前没有必要为了队列概念就增加外部组件。业务库与执行库分开仍有提交边界，需要 Outbox。若未来扩展为多实例、多用户或更高写入并发，我会重新评估共享数据库、任务分发、跨实例租约和预算一致性；不能直接宣称现有内存并发控制能支撑分布式部署。

**D7-Q5：是不是框架已经解决恢复，你只是调用了接口？**

参考答案：

> 框架解决任务持久化与恢复基础，应用层仍要定义业务身份和完成条件。例如扫描记录与 SDK 受理之间的提交缺口、同条目重复发布、取消后旧结果写入，以及有研究报告但缺少有效证据，都不是仅恢复一个函数就能解决。我在介绍工作时会具体区分框架提供的能力与实际负责的应用层改造。

**D7-Q6：如何证明这不是只有提示词的 Demo？**

参考答案：

> 需要展示提示以外的系统约束：数据库状态与提交意图、稳定身份、成功结果复用、取消 fencing、证据校验、预算预约和服务端终态检查。已有验收记录通过真实子进程终止与隔离数据库断言验证恢复，模型与来源使用 fixture 的部分只能证明工程路径。它能说明系统行为，不足以证明真实模型质量或生产可靠性已全部验证。

**D7-Q7：目前最大的不足是什么？你会如何推进？**

参考答案：

> 当前最明显的不足是实际筛选和研究质量尚未完成有人工基准的验证。下一步先审核真实来源、补齐有代表性的正负例和事件分组，完成人工主标注及独立复核；冻结 dev/test、配置与研究链，再执行 A/B/C 对照，报告召回、Top-K 精度、技术失败、费用覆盖和重复运行差异。先确定质量是否可接受，再讨论减少研究调用带来的成本收益。

**D7-Q8：如果只能讲三个亮点，你会选什么？**

参考答案：提交 Outbox 与重启对账；取消后的旧执行隔离；声明到来源快照的证据链与服务端发布检查。预算与观测可作为支撑。选择理由是每一个都能讲出具体失败场景、实现机制和边界。也可以根据真实负责范围调整，亮点多少不如解释深度重要。

### 4. 综合练习与正确答案

**D7-E1：修正一段存在错误的项目介绍。**

题目：

> 我的系统通过 Durable 保证任何请求都只执行一次。所有新闻分别启动一个子 Agent，Jev 给出真实概率，只要 Facts 高就发布。数据库保证全网新闻不重复。模拟评测没有费用，说明实现了大幅节省。用户取消后供应商立刻停止计费。

正确修订：

> 系统保存进度并复用已确认结果，但外部执行、本地未确认的请求可能重试。研究按受控批次执行，条目计划与并发分别受限。Jev 提供结构化判断，HFS 不等于事实真实概率；发布还需要有效证据和业务条件。数据库约束同条目重复发布，跨 URL 的事件关系另行判断。模拟评测验证工程路径，不能证明真实成本节省。取消使旧执行不能继续推进业务，外部已发生费用仍需要记录。

自检：应修正六类错误，即全链路 exactly-once、研究单位混淆、模型分数过度解释、唯一约束范围夸大、模拟成本推导、取消费用保证。

**D7-E2：完整分析一个异常扫描。**

教学场景：扫描已受理，SDK 接纳后进程退出；重启对账完成，进入研究；用户取消；旧研究返回一份报告和 usage；页面暂无卡片。请解释恢复、报告、费用和终态。

正确答案：

1. 恢复时使用原 requestId、payload 与会话补交并关联原提交，不新建一轮。
2. 取消先使旧 epoch 失效，再尝试中止任务。
3. 旧研究报告不能越过业务 fencing 写入或发布，也不能继续预约新的模型请求。
4. 已发生的 usage/费用可以作为迟到审计结算，不代表继续研究。
5. 用户取消流程正常收敛为 cancelled；“暂无卡片”不是 no_news 的判据。
6. 这条链路不能证明供应商只执行一次、没有费用或真实研究内容正确。

### 5. 最终闭卷过关：两轮模拟怎么做

第一轮从 D7-Q1～Q8 任选五题，允许看关键词。第二轮关闭资料，按下面五道综合题进行，每题建议回答 2～3 分钟，再追问一次。无人陪练时先录音、停顿十秒，再自行提出追问。

**F1：介绍项目，并说明你的实际工作和现阶段结果。**

标准答案要点（4 分）：用户问题与产物；主流程和技术分工；个人工作范围准确；工程验证与真实质量边界清楚。

追问：为什么不使用一个普通定时摘要脚本？

正确答法：脚本可承担采集与规则，研究阶段需要内容驱动的阅读与组织；采用 Agent 是对研究灵活性的选择，硬约束仍由代码承担，并非脚本无法实现类似产品。

**F2：业务记录存在，但执行受理状态未知，怎么处理？**

标准答案要点（4 分）：事务保存提交意图；复用原 ID/内容/会话；租约控制本地关联；对账最终补齐且不宣称外部 exactly-once。

追问：如果租约过期、旧持有者又返回？

正确答法：旧 token 不能覆盖新归属，条件更新拒绝旧关联；新处理者仍用原 requestId，租约过期不证明 SDK 未接纳。

**F3：取消和超时后，怎么避免旧研究污染结果？**

标准答案要点（4 分）：先持久 fencing；epoch/status/deadline 检查；拒绝旧业务写入与新预约；真实在途结束和迟到费用审计分别处理。

追问：调用者超时后为什么不马上再启动两个研究？

正确答法：旧请求可能仍执行，立即释放槽位会使实际并发膨胀。当前容量机制持有到真实研究结束；取消和截止是业务约束，不等于供应商即时停算。

**F4：如何让用户相信一条研究声明？**

标准答案要点（4 分）：保存并绑定来源快照；校验 hash/quote/区间；语义支持、充分性、冲突分开；发布复核且不承诺客观真实。

追问：两个来源都这样说，是否就是真的？

正确答法：可能互相转载或共同出错，不同 URL 不保证独立。系统能展示来源和支持关系，仍需可靠来源、必要的独立核查与人工评测。

**F5：如何评价质量与成本？**

标准答案要点（4 分）：人工标签与事件隔离；固定输入和研究链的 A/B/C；报告质量分母、技术失败与费用覆盖；当前未完成真实质量/账单验证。

追问：如果 B 比 A 少发很多请求，能宣布优化成功吗？

正确答法：还要看漏检和最终研究质量是否可接受，同时计入前置判断等开销和未知费用。只减少工作量可能只是漏掉了有价值内容。

最终关键错误：虚构自己的实际贡献；将 fixture 称作真实模型效果；保证全链路只执行一次；保证取消后零费用；把来源支持度称作事实真实概率。

通过条件：五题合计至少 16 分，没有关键错误，并能完成五个追问中的至少四个。追问按上述核心逻辑自评通过/不通过，不另加总分。

## 附录 A：不熟术语时先读这里

**Tool Calling：** 模型提出调用某个工具及其参数，运行时执行工具并将结果返回。模型提出调用不等于参数合法、权限足够或业务允许执行。

**Tool Schema：** 声明参数结构、类型、枚举与必填项；业务侧还要检查 item 是否属于本轮研究计划、epoch 是否有效、预算是否足够。结构校验不能替代业务校验。

**提示词与 Skill：** 提示提供行为指导，Skill 是可复用的工作指导。即使提示写“必须先研究再发布”，服务端仍应阻止缺少研究和证据时发布。当前 AgentRadar 学习重点是提示、工具和服务端约束，不要把实习项目的 climate-ds Skill 混作本项目实现。

**事务：** 将同一数据库中的一组修改作为整体提交或回滚。事务不自动覆盖网络服务或另一个独立库。

**幂等：** 同一业务动作重复请求仍保持预期效果，不额外产生重复业务副作用。需要明确身份与范围；不等于函数或网络请求从未再次执行。

**Outbox：** 与业务操作同事务保存的待提交意图；由后续处理者可靠补交。本项目用于业务受理到执行系统的衔接，不必强行引入消息队列才能称为 Outbox。

**Checkpoint：** 恢复所需的持久位置与状态。不是网页进度条截图，也不是仅供人工阅读的日志。

**Lease：** 有期限的处理归属；超时可接管，旧归属需要凭 token 条件校验，不能只依赖时间判断。

**Epoch / Fencing：** 用执行版本及状态检查使旧执行失效。它约束受保护业务动作，不改变已经发生的外部世界。

**Operation / Attempt：** 一个逻辑判断与一次实际请求尝试。重试可产生新 attempt，但仍属于同一个 operation。

**Snapshot：** 保存某个时间点的配置或正文材料，二者用途不同。快照提高可追溯性，不保证材料真实或模型输出确定。

**Top-K：** 排序后选择至多 K 个研究条目，不表示 K 个同时运行的 Agent，也不是最终一定发布 K 张卡片。

**Precision / Recall：** 精度关注选出的样本中有多少正确；召回关注全部应选样本中找回多少。应先定义任务和人工标签，再计算分母。

**Fixture / Faux：** 为可重复工程测试准备的资料与模拟模型。可以真实执行服务、数据库和进程终止，但模型语义输出仍是模拟。
