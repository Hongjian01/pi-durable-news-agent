# AgentRadar 开发改造方案

版本：v1.0｜日期：2026-10-26

目标仓库：`E:/agent/Jev/pi-durable-news-agent`

上游基线：`disler/pi-durable-news-agent`，本地初始提交 `273b79b`。该提交是阅读与对照基线，不等于已运行验收。当前仅完成 Fork、clone、upstream 配置与静态代码阅读，尚未安装依赖、启动服务或执行测试。

## 1. 产品目标与改造原则

项目名称：AgentRadar｜可恢复的主动技术情报智能体。

目标用户：关注 AI Agent 框架、SDK、模型接口和工程实践的开发者。系统周期性获取新信息，通过 Jev 进行分层语义判断，只让高价值候选进入研究 Agent，输出带来源的 Hype / Facts / Signal 卡片，并通过用户反馈调整偏好。

第一优先级是保留并证明原架构的优势：Durable 保障工作可恢复，Jev 控制高频判断成本，Agent 处理开放式研究。版本变更只是内容类型之一，第一版不演变成自动迁移或代码修复平台。

- 复用 pi-durable、Jev 客户端及现有工作流，不自建第二套执行引擎。
- 先建立原项目基线，再做小步增量；每个阶段保留离线可运行路径。
- 先修改公开产品名称、默认关注配置和交互，不全局替换 dna 路径、包名、数据库标识。
- README 区分上游已有能力、个人新增能力、个人验证工作；保留 LICENSE 与来源说明。
- 本方案中的字段、测试文件与脚本如标注“新增”，均为开发建议，不表示原仓库已经提供。

## 2. 核心功能范围

### v1 必须保留

1. 主动触发：定时 tick、手动触发、服务端是否到期判断、requestId 去重。
2. 多源采集：GitHub Releases、RSS/Atom、官方网页；支持来源开关和采集间隔。
3. Jev 六类判断：relevance、worth-attention、same-story、importance、claim-support、hfs。
4. Durable 扫描：gather、gate、dedupe、rank，以及持久 retry 状态和检查点。
5. 研究子 Agent：独立上下文、父任务所有权、有限并发、稳定提交标识及恢复。
6. 研究完成后的 HFS 分类、卡片发布、完成审计。
7. 卡片幂等写入与历史查询，保留原有故事关系与发布保护逻辑。
8. 用户“更多/更少”反馈、HFS 标签与主题/来源权重调整。
9. Web 观察任务、工具调用、Jev 判断、成本与结果；SSE 断线重连。
10. 后台上下文压缩与历史持久化，第一阶段沿用已有实现。

### v1 收缩维护范围

- 主入口只宣传 Web；CLI 保留为调试工具，TUI 暂不投入新交互开发。
- 单设备本地/单台服务器部署；保留内部 device 标识，不做多设备产品功能。
- 初始来源建议 6–10 个、关注主题 3–5 类；这是开发起点，不是质量指标。
- 卡片界面优先展示摘要、HFS、来源、研究依据和建议动作；先保留底层组件枚举，逐步精简。
- 图片生成默认关闭；必须补齐无图片发布路径，不依赖图像 API key。
- Firecrawl、复杂深搜和自动发现来源作为可选增强，不作为首个演示的前置条件。
- 复杂时间线默认不展示，但暂不删除同故事去重、成员关系和版本发布逻辑。

### v1 不做

多租户、支付、自动升级依赖、自动修改用户仓库、自动部署、移动端、向量知识库整合、模型训练、完整框架重写。这些不作为完成项目的必要条件。

## 3. 已有架构与改造落点

以下路径均相对于目标仓库根目录。

- `apps/dna-server-cron/src/tick.ts`：时间槽请求标识、重试、调用工作流。
- `apps/dna-server-api/src/routes/workflows.ts`：工作流 API 与扫描结果查询；现有启动接口仅允许 cron token。
- `apps/dna-server-api/src/news/sweep.ts`：扫描生命周期与触发协调。
- `apps/dna-server-api/src/news/sweep-task.ts`：持久采集/筛选/去重/排序；扩展检查点与故障验证的核心入口。
- `apps/dna-server-api/src/news/{stories,rank,hfs,taste,audit}.ts`：故事匹配、排序、评分、偏好与完整性审计。
- `apps/dna-server-api/src/agents/tools/{research-items,report-findings,jev-classify,present,complete-sweep}.ts`：研究到发布的业务工具。
- `apps/shared/packages/durable-agent/src/{harness,tools,subagents}.ts`：运行容器、重放辅助、子 Agent 所有权。
- `apps/shared/packages/jev/src/{client,command,policy,ledger}.ts`：契约、命令、阈值与调用记录。
- `apps/dna-server-api/prompt_engineering/jev/<command>/command.json`：六类判断定义；领域化策略的优先改造点。
- `apps/dna-server-api/prompt_engineering/agents/`：主 Agent 与研究角色提示词。
- `apps/dna-server-api/src/db/migrations/001_schema.sql`：现有领域库；增加字段采用后续迁移，不直接改已应用的 001。
- `apps/shared/packages/dna-sdk/src/`：API、类型与流归并；新增接口先改契约，再改服务和前端。
- `apps/dna-client-browser/fe/src/components/{SweepDetail,RunTree,ToolDetail,ExecutionsView,CardDetailDialog,HfsPill}.vue`：主要展示入口。

注意：现有 `dna.news-sweep` 状态机只覆盖 gather/gate/dedupe/rank/retry。研究、HFS、发布及完成审计由后续 Agent 工具与任务处理，不应在文档或 UI 中声称它们已是同一个持久任务的 phase。

逻辑处理链：

```text
tick / 手动请求
  → API 校验与触发去重
  → news-desk Agent
  → dna.news-sweep 持久任务 [gather → gate → dedupe → rank]
  → 研究子 Agent / report-findings / claim-support
  → hfs
  → present_news
  → complete_sweep 审计
  → Web 观察与用户反馈
```

## 4. Durable 改造设计

### D1：检查点和恢复过程可解释

先梳理每个阶段的输入、已持久化结果、游标与转移条件。给观察界面增加“当前阶段、最近检查点、重试次数、下一次重试时间、任务关联”的可读展示。

已有数据能推导的字段不新增数据库副本。确有缺失时，通过迁移新增重试/恢复事件记录；时间用于展示与诊断，不能作为唯一幂等键。

### D2：明确三层去重

1. 触发去重：同 requestId 复用扫描，不生成第二个相同扫描。
2. 研究去重：同工具任务重放复用已有子会话和稳定 requestId 的提交。跨不同扫描是否可复用属于新增缓存策略，不混同现有保证。
3. 发布去重：复用 tool task receipt、工具调用标识和 item/card 唯一约束；多次恢复后卡片计数与实际记录一致。

检查现有唯一约束能否覆盖目标业务，再补迁移与测试，避免在应用层先查后写却没有数据库保护。

### D3：复用判定结果时带上版本边界

为领域化判断设计可追踪指纹：规范化判断输入、相关偏好上下文、问题内容/版本、模型标识、抽取策略版本。使用确定性序列化后哈希；相同文章但问题或用户偏好改变时，不能无条件复用旧结果。

先核查原有 ledger 与缓存语义，只补缺少的内容。保留历史判定供审计，不覆盖旧结论。`latest` 模型别名不能提供稳定模型版本保证，评测优先固定可用的版本标识，并记录服务返回的 resolvedModel。

### D4：明确重放边界

- `once()` 是检查 memo → 执行副作用 → 保存 memo。外部操作成功但 memo 未提交时崩溃，可能重做。
- `onceInCommit()` 适用于能与收据放在同一持久事务中的内部操作，不能据此推导外部请求恰好一次。
- 业务库与 harness 存储若不是同一事务域，不宣称跨库原子提交；依靠唯一键、状态对账与重试恢复。
- 不修改 pi-durable 核心存储引擎；在应用层补足业务幂等与证据。

验收用语：已提交结果可复用、研究任务重放不重复创建、业务发布幂等；不承诺所有远端计费请求永不重复。

## 5. Jev 改造设计

六类命令全部保留，第一版只修改场景定义与可观察性，不替换为主模型自由输出。

- relevance：围绕 Agent 开发、工具调用、运行时、检索和工程实践；支持中英文术语。
- worth-attention：区分有实际变化或证据的信息、重复宣传、无细节预告。
- same-story：区分同一事件重复报道与同一框架的新进展；低置信度不强制合并，可交研究复核。
- importance：输出重要性；主题权重、来源权重、新鲜度仍由代码组合。
- claim-support：判断提供材料是否支持特定主张，保留材料和对应片段；高分不等于独立查证。
- hfs：保留三维独立评分，中文界面可标注“炒作程度 / 证据可核验度 / 行动价值”。

将阈值与评分题分开维护。先沿用原默认值，再通过开发集调参；测试集不能用来反复挑阈值。记录问题版本、输入指纹、原始答案、策略判决、耗时及 reported/estimated/unknown 成本来源。

新增建议：`docs/judgment-policy.md` 记录每类判断定义、边界案例与阈值理由。先不开发模型后端替换平台，避免稀释 Jev 主线。

## 6. 业务与 Web 改造

公开品牌和文案改为 AgentRadar，默认关注 Agent 工程领域。第一版不改 `@dna/*` 包名、API v1 标识、数据库目录和 tool 名，以免扩大兼容性影响。

Web 保留三类视图：

1. 情报流：摘要、来源、HFS、研究依据、反馈。版本变化作为卡片内容，不承诺对用户项目作精确影响判断。
2. 执行详情：扫描进度、研究任务树、工具调用、Jev 判定、成本与错误。
3. 配置：关注主题、来源、扫描间隔、每轮候选数、模型与研究并发的必要设置。

前端显示阶段必须基于服务端状态，不根据聊天文本猜测进度。刷新与断线重连读取 snapshot 并继续消费 deltas，不自动重发原触发请求。

图片默认关闭涉及 `present.ts`、图片服务、SDK 卡片类型、渲染与工具提示词；不能只隐藏图片节点，否则仍可能产生后台图片任务。

仅在受信 hub/server 中使用 cron token；浏览器不得持有它。手动扫描入口优先沿用已授权的服务端路径，不直接放宽原工作流鉴权。

暂不删除 CLI/TUI：`apps/shared/packages/dna-sdk/tests/capabilities.test.ts` 检查各客户端能力覆盖。后续若真移除客户端，需要同时调整 workspace、能力声明、测试、just 脚本与文档，另开独立改动。

## 7. 数据与契约变更原则

- 优先复用 sources、items、sweeps、findings、stories、cards、jev_calls 等已有实体。
- 新增恢复事件、判断指纹或版本字段前，先确认现有 schema 与 ledger 是否已包含等价数据。
- 新增持久字段走增量 SQL migration；完成从原基线数据库升级的验证。
- SDK 类型、服务端响应、stream reducer 和 Web 展示在同一功能批次更新。
- 不把长期运行业务进度只存入前端 store；不通过删库解决迁移问题。
- benchmark 数据与应用运行数据分开存储，避免对照实验污染生产偏好及历史去重结果。

## 8. 实施顺序与阶段验收

### M0：基线运行与机制梳理

任务：保留原功能，安装依赖；跑通 fixture/faux；执行类型检查、核心测试和 Web build；用少量真实输入验证 Jev 与主模型分别可用。

环境：要求 Node >=24。当前主机为 Windows，先检查已有 Node、WSL、just；Linux shell/cron 脚本不能直接假定可运行。优先选择可用的 WSL/Linux 跑原演示，或保留 npm 核心命令并新增独立 Node 调度入口。原 cron 的 install/uninstall 与测试含 Unix 依赖，需隔离，而非随意跳过全部测试。

产物：`docs/baseline.md`，包含 commit、运行环境、测试结果、失败项与原始演示记录。

通过条件：离线扫描完整生成卡片；已确认失败来自环境还是逻辑；真实 API 验证单独记录且不与 mock 结果混用。完成前不做全局重命名。

### M1：产品收敛与无图片路径

任务：公开名称、中文文案、默认主题/来源；实现图片开关的服务端路径；Web 重点展示三类视图。默认低频、小批量运行。

产物：品牌与来源配置提交、无图片发布路径测试、第一份可用页面。

通过条件：未配置图片 key 也能完成扫描；HFS、反馈、研究、恢复和实时观察仍保留；CLI/TUI 原能力未被误删。

### M2：Durable 补强与故障实验

任务：梳理并补齐 D1–D4；增加研究恢复、发布边界与持久重试验证；展示恢复事件。

产物：故障注入工具/测试、结果记录、幂等键与事务边界说明。

通过条件：下文恢复场景均有可复现脚本和断言；失败路径不依赖人手重新创建扫描。暂停调度、停止进程与取消任务语义分别说明，取消后的任务不得自动复活。

### M3：Jev 领域策略与证据输出

任务：版本化六类判断；整理中英文正反例和低置信度策略；展示原始答案与代码判决；研究结论关联来源依据。

产物：判断策略文档、固定样本、证据展示与契约测试。

通过条件：同故事新进展不会被无条件吞掉；Facts 不显示为真假概率；偏好/问题变化不会误用旧缓存。

### M4：对照评测与发布材料

任务：冻结开发版本，在固定数据上评测质量、成本和耗时；完成恢复录像、架构文档、README 与贡献清单。

通过条件：真实与模拟实验明确标注；实测数字可复现；新用户能按文档跑通离线演示；提交变更只包含代码、文档、脱敏样本和必要资源。

推荐提交顺序：基线文档 → 产品配置 → 图片开关 → 恢复观察 → 故障测试 → Jev 策略 → 证据展示 → benchmark → README。每批只处理一个可验收目标。

## 9. Durable 必测场景

1. 相同 requestId 连续或并发触发：只有一个对应扫描；同时验证不同 requestId 在已有扫描运行时的既有策略，不能默认所有请求都会排队。
2. gate 已提交部分结果后杀进程：已完成条目不重复判断，剩余条目完成。
3. 研究子会话创建后中断：恢复后复用相同 ownerTaskId 对应的孩子，不新增一套研究会话。
4. 研究提交后中断：稳定 requestId 对应提交不重复接纳；父任务最终拿到结果。
5. Jev/页面读取短暂失败：重试次数和截止时间可解释，重启后重试预算不清零。
6. 卡片业务写入后、工具结果保存前中断：重复执行不新增同 item 的第二张卡片；计数与表记录相符。
7. 浏览器断连/刷新：后端继续执行，重连展示正确快照，不重新触发扫描。
8. 付费请求成功、本地结果未保存时中断：用桩复现歧义窗口，记录可能重复而非错误断言绝不重付费。
9. 旧数据库升级：既有扫描、卡片和任务关系可读取，新增迁移不破坏已完成记录。

故障注入只用于测试运行与临时数据目录，不对真实长期运行库做破坏性实验。原有 `tests/recovery.test.ts` 是起点，不把它改名后当作新增验证。

## 10. Jev 与成本评测

建议第一版整理约 100–200 条人工标注候选，包含相关/不相关、宣传性内容、重复报道、同框架不同事件、中英文与信息不足案例；这是工作量建议，不是预期成果。按故事簇/时间切分开发集与测试集，避免同故事报道跨集合泄漏。

- 相关性：precision、recall，报告被提前误删的高价值条目。
- 去重：匹配对 precision/recall；另列错合并导致信息丢失的案例。
- 排序：固定 Top-K 的人工相关性或标注收益，记录 K 与标注准则。
- HFS：按各维度的标注规则评估误差或一致率；不报告“新闻真实率”。
- 证据：人工检查主要结论是否有提供材料支持；把 URL 存在和证据支持分开统计。

成本对照至少两组：

A. 相同候选经相同基础清洗与精确去重后，全部进入相同研究流程。
B. 相同候选增加 Jev 相关性、语义去重和排序，再选择候选研究。

两组固定来源快照、主/研究模型、输出要求与预算口径；B 额外计算全部 Jev 成本；报告总成本、每个有用结果成本、研究数、input token、墙钟耗时和质量差异。缓存冷/热分开报告；每组使用独立测试数据目录。可另设等研究预算对照，用于区分少研究与筛选本身的收益。

费用优先使用供应商 reported cost；估算值标记 estimated，未知记 unknown，不能按 0 计入。保存原始运行记录；供应商未返回账单时，不能凭本地 mock 证明真实省费。


现有 Linux/WSL 原生入口：`just combos dev`（离线演示）、`just test faux`（工作流与恢复等测试）、`just test ui`（浏览器）、`just check`（项目规定检查）。使用前以 `just --list` 核对 recipe 名称与环境；浏览器测试另需浏览器依赖，真实测试可能产生费用。

根 `npm test` 会包含各 workspace 的测试，含浏览器或环境相关入口，不将它等同于纯离线单元测试。M0 要确定并文档化真正离线的检查集合。新增脚本优先复用已有 tsx/node:test 工具，不另引入任务框架。
