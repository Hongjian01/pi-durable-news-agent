# 跟着一条技术更新学懂 AgentRadar

日期：2026-10-29。用途：把流程图上的每个方框，转化成可以理解的输入、调用、处理、保存和输出。

若要进一步学习研究子 Agent 的创建、模型与工具循环、结果汇总及恢复，请读 [跟着六条新闻学懂研究子 Agent](subagent-mechanism-walkthrough.md)。该专题含五阶段学习计划、贯穿数据文件与练习答案。

本文依据当前仓库实现编写，是纸面教学案例，不是已运行的真实模型轨迹。OrbitKit、网址、ID、分数和结果均为虚构；具体字段示意会省略无关信息，不是可以直接复制发送的完整 API 请求。本文不要求运行项目或定位代码。

## 一、这是不是第一天需要掌握的？

**第一天需要沿一个案例理解正常主线；不要求同一天掌握所有异常、数据库细节和恢复机制。**

对照七天计划这样使用本文：

- **第一天：**读案例设定、正常流程各步的“第一天先记住”和最后的第一天验收题。先理解系统接收什么、谁处理、产出什么。建议占用原计划 50 分钟学习时段中的 30～40 分钟，不额外增加一天的总任务。
- **第二天：**重读第 4～7 步，理解 Jev 的输入、事件关系、排序及研究批次。
- **第三天：**重读上下文、结果保存，以及异常案例中的进程退出和结果复用。
- **第四天：**深入第 1～2 步和取消案例，掌握 Outbox、两种请求身份和 epoch。
- **第五天：**深入第 8～12 步，掌握快照、引用、支持判断和发布核验。
- **第六天：**深入重试、预算和终态，区分错误、未知和正常无新闻。
- **第七天：**脱离本文，讲完正常路径，再任选一个异常场景解释。

第一天不必背住表名、阈值、哈希、字符区间算法、租约与版本检查。若这些不熟，不影响第一天过关；但“主 Agent、Jev、研究子 Agent、业务代码各做什么”应当分清。

## 二、先认识案例中的新闻与角色

### 1. 虚构新闻

用户关注“Agent 框架”和“持久会话”。一个已配置的官方 RSS 来源出现文章：

```text
标题：OrbitKit 2.4 发布：增加可恢复会话
URL：https://orbitkit.example/blog/2-4
发布时间：2026-10-28 09:00（北京时间）
摘要：OrbitKit 2.4 增加可恢复会话，面向 Agent 开发者。
```

假设用户在 2026-10-29 09:00 发起新扫描；来源抓取成功，历史中没有该版本的已有卡片，本轮配置最多选择 1 个候选。为聚焦流程，假设其他来源和搜索也正常完成，且没有比本条更优先的候选，没有未处理的来源线索。

文章实际正文在教学设定中完整、未截断、超过抓取路径的最小正文长度，开头为：

```text
Version 2.4 is available.
Resumable sessions are supported.
```

以上只展示开头，不表示只保存这两行，也不表示任意几十字短页面都能被当前正文提取路径接受。稍后我们只核验第一句所支持的“2.4 版本已发布”。

### 2. 教学 ID

这里只需要理解各对象不能混用，不要求记数字。

- `sweep=42`：整轮扫描。
- `context=77`：本轮冻结的配置与策略。
- `submission=900`：Durable 接纳的输入提交。
- `item=101`：这条新闻候选。
- `snapshot=301`：本轮读取的来源正文。
- `report=401`：研究报告。
- `card=601`：最终新闻卡片。

关系可以读成：“扫描 42 发现条目 101；条目研究读取快照 301、保存报告 401，最终形成卡片 601”。一个扫描可以有多个条目，不同对象不能因为数字相近就当成同一种东西。

### 3. 谁在做事

- **API 和业务代码：**接收请求，检查状态、预算、证据，保存数据。
- **主 Agent：**收到任务，通过工具组织扫描、研究、展示和完成。
- **持久扫描子任务：**按检查点执行采集、筛选、事件关联和排序。
- **Jev：**根据提供的材料回答结构化判断问题，不直接写最终卡片。
- **研究子 Agent：**使用读取等工具获取材料，组织摘要、声明和引用。
- **Pi Durable：**承载会话、任务和工具的持久运行与恢复基础。

一句话区别：**Agent 提出工具调用，运行时代为执行；Jev 给判断值，业务代码按规则处置；数据库保留结果。**

## 三、正常路径：从用户扫描到一张卡片

### 第 1 步：用户发起扫描，系统受理

**第一天先记住：**系统先建立“这一轮任务”的记录，再开始发现新闻；此时还不知道会发现 item=101。

**输入是什么？** 用户点击“立即扫描”。客户端带有本次请求身份，例如 `learn-request-42`。本轮最多选择 1 张候选是教学设定，不是系统固定只能处理一条。

**谁处理？** API 调用扫描受理逻辑，确定性代码执行检查。

**具体怎么做？**

1. 检查同一个请求是否已经受理，重复则返回原扫描。
2. 检查是否存在活动扫描等前置条件；定时请求还要检查是否到期。
3. 新建扫描 42，初始状态为 queued。
4. 保存本轮上下文 77，包括主题、来源、权重、提示、模型、预算和参考时间。
5. 同事务保存 Outbox 提交意图与完整提交草稿。

**保存什么？** 逻辑上可以理解为：

```text
扫描：42，queued，来自手动操作
请求身份：learn-request-42
上下文：77，固定本轮偏好、预算与参考时间
待提交意图：向 Durable 主会话提交本轮任务
```

这是业务含义示意，不是完整数据库行。后续新闻条目还未出现。

**输出是什么？** 返回本轮扫描身份和受理情况，供页面观察；接下来处理提交意图。新请求尚未受理、仅返回 skipped 或 not_due 时，不会执行后面的整条正常路径。

**自问：为什么还没抓新闻就要保存任务？**

答案：需要先确定本次工作身份、采用的规则与恢复依据；否则进程退出后可能不知道原来承诺执行什么。

### 第 2 步：把扫描任务可靠提交给主 Agent

**第一天先记住：**受理业务任务和让 Agent 真正收到任务，是两个动作，中间有可靠提交机制。

**输入是什么？** Outbox 中保存的提交草稿。内部提交 ID 使用 `sweep:42`，与客户端的 `learn-request-42` 职责不同。

**谁处理？** 提交对账代码调用 Durable 主会话的 submit。

**具体怎么做？** 领取待提交意图，用原内容和内部 requestId 提交，取得 submission=900，再关联回 sweep=42。完整草稿含本轮扫描 ID 和调用工具的任务说明。

**保存什么？** Outbox 状态由待处理变为 linked，扫描关联 submission=900；Durable 执行存储保留该提交与后续会话/任务记录。

**输出是什么？** 主 Agent 收到“处理 sweep 42”的输入，然后调用：

```json
{"tool":"run_news_sweep","arguments":{"sweep_id":42}}
```

这是便于理解的调用示意，不是完整模型协议。

**自问：是 API 直接让 Jev 生成最终新闻吗？**

答案：不是。先让主 Agent 启动扫描工具；该工具创建或复用持久扫描子任务，再执行四个阶段。

### 第 3 步：gather，采集并形成新闻条目

**第一天先记住：**抓取程序从配置的来源或搜索结果中发现文章，将其保存成候选条目。模型不必负责解析每一条 RSS。

**输入是什么？** 本轮来源计划、搜索主题、时间窗口和候选数量限制。

**谁处理？** 持久扫描任务调用来源适配器和搜索服务；RSS、Atom、网页等由相应抓取逻辑处理。

**具体怎么做？** 来源返回条目列表，系统处理条件请求、内容变化与缓存。当前案例 RSS 出现 OrbitKit 2.4；程序提取 URL、标题、摘要、日期等信息，缓存来源内容，再插入或复用新闻条目。

**保存什么？**

```text
来源缓存：文章的标题、URL、摘要等
item 101：属于 sweep 42，状态 candidate
本轮来源处理状态：成功
本轮条目处置：仍待判断
```

**输出是什么？** 类似下面的候选信息进入 gate：

```json
{
  "id":101,
  "title":"OrbitKit 2.4 发布：增加可恢复会话",
  "url":"https://orbitkit.example/blog/2-4",
  "excerpt":"OrbitKit 2.4 增加可恢复会话，面向 Agent 开发者。",
  "status":"candidate"
}
```

这是简化条目视图。此时只是“发现了文章”，不是“已证明文章内容真实”。RSS 摘要缓存也不能直接冒充可核验证据快照。

**自问：下一步为什么不能直接发布？**

答案：尚未判断相关性、事件关系、研究价值与证据，当前只有来源提供的候选信息。

### 第 4 步：gate，判断相关性和关注价值

**第一天先记住：**Jev 判断内容是否符合用户关注，代码决定保留或过滤，结果会保存。

**输入是什么？** 标题、来源、可用摘要/正文片段、关注主题和适用反馈等。不同命令使用各自需要的材料。

**谁处理？** 扫描任务调用 Jev 的 relevance 和 worth-attention。外部请求实际发送前要经过预算等约束。

**具体怎么做？**

1. 构造“与当前用户主题是否相关”的判断材料。
2. 构造“是否值得关注、是否有新信息”的判断材料。
3. 校验返回结构，提取业务使用的数值。
4. 代码应用本轮策略，不由模型直接修改条目状态。

**假设输出是什么？** 为方便学习，使用处理后的简化视图：

```text
relevance = 0.90
matchedTopic = Agent 框架
worth = 0.85
novelty = 0.80
```

这些是假设的归一化判断结果，不是原始供应商响应，不是事实真实概率。假设它们满足本轮门槛，条目保留为候选。

**保存什么？** 条目上的分数与匹配主题、本轮处置原因、逻辑 judgment operation 和实际 attempt 等记录。operation 表示这项判断，attempt 表示某次真实尝试；发生重试时可能一项判断对应多个尝试。

**下一步是什么？** 进入事件关联。未通过门槛的条目被标记过滤，不送入正常研究路径；调用错误则另记，不能当作分数为零。

**自问：模型返回“相关”后，程序还做什么？**

答案：检查返回结构、按策略解释结果、保存判断与条目处置，然后推进检查点。

### 第 5 步：dedupe，判断是否已经报道过

**第一天先记住：**相同事件可能有多个 URL，系统要分清重复报道、补充证据和新进展，不能只比标题是否相等。

**输入是什么？** item=101，以及从历史记录中召回的可能相关条目。本案例假设历史中有 OrbitKit 2.3 的报道，没有 2.4 的已有卡片。

**谁处理？** 事件匹配代码先找候选，再调用 Jev 的 same-story 判断；后续关系处置由代码完成。

**具体怎么做？**

1. 用文本特征召回可能相关的历史条目，限定候选和材料大小。
2. 读取比较所需的候选与历史材料；这里就可能抓取正文，不一定等研究阶段才首次抓取。
3. 让 Jev 判断是否同事件、是否已有覆盖、是否新发展或补充，以及材料是否充分。
4. 根据规则产生 duplicate、evidence、development、different 或 uncertain 等处置。

**本案例假设输出：**2.4 的发布属于新的发展，保留 development 身份进入排序。版本不同不自动保证这个结果；仍需结合内容及本轮规则。

**保存什么？** 事件关系、判断材料/结果，以及条目与事件的关联。若已在本阶段读取正文，也可能同时生成后面要复用的来源快照。

**下一步是什么？** 需要独立研究的新发展继续排序；重复报道或补证可关联已有事件，不必再新增卡片；不确定关系不能直接压成重复。

**自问：唯一索引能完成这里的判断吗？**

答案：不能。唯一约束可限制同条目重复发布，不能理解两个不同 URL 是否报道同一事件。

### 第 6 步：rank，决定本轮优先研究谁

**第一天先记住：**通过筛选不表示一定研究，还要排序并受本轮名额限制。

**输入是什么？** 保留条目、用户主题/来源权重、发布时间和冻结参考时间。

**谁处理？** Jev 提供 importance；代码计算综合排序、安排事件优先级并选择候选。

**具体怎么做？** 本例假设 importance=0.8，主题权重=1.5，来源权重=1。新闻距离本轮参考时间恰好 24 小时，新鲜度因子为 1：

```text
排序值 = 0.8 × 1.5 × 1 × 1 = 1.2
```

代码还会优先给不同事件分配名额，再考虑同事件的后续发展。本轮只取 1 个候选，假设 item=101 被选中。

**保存什么？** importance、selected 标记与研究计划。未选条目有明确的 not_selected 处置，不需要本轮都研究完。

**输出是什么？** `run_news_sweep` 返回候选 ID、标题等概要给主 Agent。工具返回主要是文本及附加信息，不应把这里的教学对象示意当作实际完整 JSON 返回。

**自问：返回候选是不是表示整轮扫描完成？**

答案：不是，只是四阶段扫描子任务完成。主 Agent 还需要安排研究、分类、发布和最终核验。

### 第 7 步：主 Agent 调度研究子 Agent

**第一天先记住：**主 Agent 把指定候选交给研究子 Agent，研究范围不是子 Agent 任意扩大。

**输入是什么？** 候选 101 与本轮 sweep 42。

**调用示意：**

```json
{
  "tool":"research_items",
  "arguments":{
    "sweep_id":42,
    "batches":[{"item_ids":[101],"focus":"核实版本与可用状态"}]
  }
}
```

**谁处理？** 研究工具检查计划后，通过项目封装在 Pi Durable 上创建或复用研究子会话。

**具体怎么做？** 校验条目属于选中计划、没有重复、数量和容量允许；保存研究任务，绑定原 sweep、epoch、条目集合和截止；构造研究提示，再按并发容量执行。重放时查找原有子会话，而不是无条件新建。

**保存什么？** 研究工作记录、子会话关联与原执行绑定。示例只研究 1 条，不表示真实工具只能一个批次一个条目。

**输出是什么？** 子 Agent 开始研究；工具最终将其研究结果概要返回主 Agent。期间可能有多轮模型请求和工具调用，不是“启动一次模型调用即完成研究”。

**自问：Jev 和研究子 Agent 是否在做同一件事？**

答案：Jev 回答结构化判断；研究子 Agent 组织多步读取、整理与报告，两者职责不同。

### 第 8 步：读取正文，取得可引用的来源快照

**第一天先记住：**研究子 Agent 通过工具拿到真实保存的正文，后续引用必须指向这份材料。

**输入是什么？** `read_item` 的 item_id=101。工具根据条目找到 URL 与缓存。

**谁处理？** 读取工具和正文读取代码进行 HTTP、正文提取与缓存；研究子 Agent 消费工具返回的文本。

**具体怎么做？** 若本轮已有固定快照，优先复用它；否则按当前读取路径获取正文，提取并保存规范化文本，绑定本轮 URL 与快照。来源摘要不够时，研究过程中可以补充抓取；不是每次 read_item 都重新下载。若事件关联阶段已经读过正文，这里可能直接取得原快照 301。

**保存什么？**

```text
snapshot=301
所属本轮：sweep=42 的 URL 绑定
正文：规范化后的完整正文
body_hash：该正文的 SHA256
fetched_at：实际获取时间
truncated：否
```

这仍是概念视图，hash 应由程序计算；本文不伪造一个看起来正确的哈希值。

**输出是什么？** 研究子 Agent 看到标题、来源、已有分数、snapshot ID、hash、获取时间，以及正文片段。本文正文开头的第一句为 `Version 2.4 is available.`。

**自问：只给一个网址能完成证据链吗？**

答案：不能。网址会变，系统需要保存本轮读取的具体正文，引用才能被重新定位与核对。

### 第 9 步：提取声明与原文引用

**第一天先记住：**研究子 Agent 写出要表达的事实声明，并指出原文哪句话支持它。

**输入是什么？** 读取工具返回的材料与研究要求。

**谁处理？** 研究子 Agent 组织报告，调用 `report_findings` 提交。

**调用示意：**

```json
{
  "tool":"report_findings",
  "arguments":{
    "item_id":101,
    "summary":"OrbitKit 发布 2.4 版本，新增可恢复会话；适合关注持久执行的开发者进一步评估。",
    "claims":["OrbitKit 2.4 版本已发布"],
    "citations":[{
      "claim_index":0,
      "snapshot_id":301,
      "quote":"Version 2.4 is available.",
      "start":0,
      "end":25
    }],
    "evidence_urls":["https://orbitkit.example/blog/2-4"],
    "actionability":"medium"
  }
}
```

当前 Schema 允许 body_hash 省略，研究提示要求保留读取时的 hash；此例为避免虚构 hash，只展示其他引用字段。若携带 hash，必须使用工具返回的真实值。服务端仍会核对保存正文的内容身份。

**具体怎么做？** 声明用中文表达，quote 保留来源原文，不把中文翻译冒充英文原句。start=0、end=25 是 UTF-16 左闭右开区间；该 ASCII 句子长度为 25，所以切片恰好取得整句。

**保存什么？** 此刻是“提交待验证报告”，服务端还要先完成下一步检查，再保存最终报告与声明状态。

**自问：摘要每一句都被这一个引用证明了吗？**

答案：没有。本例只有“版本已发布”这一条声明进入引用校验；其余摘要和行动建议属于研究分析，不能因为同卡片中有 supported 声明就当成全部逐句核实。

### 第 10 步：服务端检查引用，再由 Jev 判断支持关系

**第一天先记住：**先检查引用是否真的存在，再判断它能否支持声明；检查由工具服务端执行，不是相信子 Agent 自报成功。

**输入是什么？** 上一步的 claim、citation、允许的来源 URL，以及数据库中的快照 301。

**谁处理？** `report_findings` 内部调用证据评估逻辑；确定性代码校验引用，Jev 的 claim-support 评价语义关系。

**具体怎么做？**

1. 快照是否属于 sweep 42，引用 URL 是否属于提交的允许来源。
2. 区间是否有效，正文 `[0,25)` 是否等于 quote，正文 hash 是否一致。
3. 正文是否被截断，是否有足够的有效证据。
4. 将声明、有效引用及周边上下文交给 Jev，取得支持度、充分性和冲突判断。
5. 按本轮策略计算 supported、unsupported、insufficient 或 conflicting。

**本案例假设输出：**支持度=.90、充分性=.90、冲突=.10，引用有效且未截断，得到 supported。它表示当前材料支持声明，不是声明有 90% 客观为真的实测概率。

**保存什么？** report=401、finding、claim 状态、引用与 snapshot 的对应关系、本次判断 operation，以及本轮研究状态。若没有有效 supported 声明，会留下证据不足处置，而非假装通过。

**输出是什么？** 工具向研究子 Agent 返回报告已保存及支持情况；研究工具最终把研究概要返回主 Agent。

**自问：这一步是新增一个独立 Agent 吗？**

答案：不是。它是报告工具服务端执行校验并调用 Jev。一次工具调用内部可以包含数据库操作和模型判断。

### 第 11 步：完成 HFS 分类与展示选择

**第一天先记住：**研究有了结果后，还要决定情报的性质与展示形式；HFS 不是事实核验的替代品。

**输入是什么？** 标题、正文/摘要、本轮研究结果、分类偏好等。

**谁处理？** 主 Agent 调用 `jev_classify` 的 hfs 命令；代码解释分数并保存分类，主 Agent 按可选组件组织展示。

**调用示意：**

```json
{"tool":"jev_classify","arguments":{"command":"hfs","item_id":101}}
```

这是关注关键字段的教学示意，其他调用参数以实际工具 Schema 为准。研究过程中也可能按需做分类，这里展示主线顺序，不是强制唯一时序。

**假设输出是什么？** 处理后的 HFS 视图中，Facts 与 Signal 较高，Hype 较低。本例不强行设置互斥标签或固定卡片组件，以免把假设分数冒充完整策略结果。

**保存什么？** 本轮 HFS 分类记录、相关判断与展示所用信息。Facts 表示文本可检查性，不能解读为真实正确率。

**下一步是什么？** 主 Agent 从实际允许的卡片组件中选择适配形式，填写标题、摘要等，调用 present_news。

**自问：HFS 高分是不是就可以直接发布？**

答案：不是。还需要研究、证据、条目计划和展示参数等发布检查。

### 第 12 步：发布检查，保存卡片

**第一天先记住：**主 Agent 请求展示，服务端确认条件满足后才真正写卡片。

**输入是什么？** item=101、选择的合法组件及标题摘要等参数。本案例假设参数和分类兼容。

**谁处理？** `present_news` 工具服务端。

**具体怎么做？**

1. 检查重放结果或已有同条目卡片，存在则复用。
2. 检查事件角色，本例是可独立展示的 development。
3. 校验组件及其参数是否与分类适配。
4. 检查条目已选中、研究完成、HFS 存在、具有有效支持声明。
5. 从服务端有效记录生成 verifiedClaims，不信任 Agent 自填的核验列表。
6. 在业务事务中写卡片、关联、事件与计数，唯一约束防止同 item 重复新闻卡片。

**保存什么？** card=601，关联 item=101 和本轮业务记录；可展示的 supported 声明指向 snapshot=301。其他卡片分析文案不因而被证明真实。

**输出是什么？** 工具返回卡片身份等结果；服务端发布数据事件，Web 获取并显示卡片。

**自问：页面负责生成和保存最终卡片吗？**

答案：不是。发布发生在服务端，页面负责展示；刷新不会重新研究或再次发布同一条目。

### 第 13 步：最终核验，关闭本轮扫描

**第一天先记住：**发出一张卡片和整轮业务完成是两件事，最后由服务端检查全局缺口。

**输入是什么？** 本轮来源、所有条目、研究、判断操作、预算与发布记录。本文虽然聚焦 item=101，但完成判断要覆盖整轮，不能只看这一条。

**谁处理？** 主 Agent 调用 complete_sweep，服务端持久保存完成请求并进行 finalization。

**具体怎么做？** 检查扫描阶段是否完成、来源是否有错误、条目是否均有明确处置、是否有未结束研究/失败判断、发布条件和预算缺口。必要时返回有限修复要求，不直接相信模型说“成功”。

**本例输出：**假设其他工作也正常、没有缺口、已有 card=601，因此 sweep=42 变为 completed。

**其他结果：**

- 无缺口、无新闻卡片：no_news。
- 有未修复缺口、有可用结果：常规核验路径得到 partial。
- 有未修复缺口、无可用结果：failed。
- 用户取消：走取消生命周期，正常收敛 cancelled，不由零卡片推断 no_news。

**保存什么？** 终态、摘要、缺口/审计记录、结束时间和本轮卡片数等。

**自问：这轮完成后，下一轮是什么关系？**

答案：下次新扫描有新身份与新上下文，可使用历史事件与用户偏好，但不应无条件重发原 item=101；原扫描中断后的恢复仍继续原身份。

## 四、把同一案例加入失败、重试与恢复

本节第一天只需知道“这些异常有独立机制处理”，细节分别放到第三至第六天学习。每个场景都从正常案例分叉，不是同一次演示中真的连续发生了所有故障。

### 场景 A：Jev 的 worth 判断被限流——第二、三、六天深入

**出事位置：**第 4 步 relevance 已成功保存，但 worth 请求返回 429。

**系统拿到什么？** 一项成功判断与一项错误，而不是“相关性高、价值为零”。

**接下来怎么做？** 判断请求按其重试分类保存等待时间与 attempt，受次数、截止和预算限制；允许时等待后继续。恢复或重新进入阶段时，可以复用已经确认的 relevance，而非全部重算。

**最后可能是什么？** worth 重试成功则继续；耗尽后记录错误，完成核验可能发现缺口并收敛 partial/failed。不能把 429 写成 filtered 再伪装正常无新闻。

**范围提醒：**这是 Jev 判断请求场景。来源抓取的 429 有不同处理，不要概括成所有 HTTP 429 都使用同样重试规则。

**练习：重试只针对失败判断，是否说明完全没有新增费用？**

答案：不能。新的实际尝试可能收费，已成功判断的复用只是减少重复工作；所有尝试仍应被预算与审计覆盖。

### 场景 B：SDK 已接纳，但业务关联未写回就退出——第四天深入

**出事位置：**第 2 步 Durable 已接纳 submission=900，但 Outbox 还未关联成功，进程退出。

**保存了什么？** 业务库保留 sweep=42、context=77、原提交草稿与内部 requestId=`sweep:42`；执行库保留原提交。它们还未完成本地关联。

**重启怎么做？** 对账程序使用原会话、原 requestId 和原内容提交，取得已有受理结果，再关联 submission=900。不创建 sweep=43 来冒充原扫描恢复。

**为什么租约不够？** 租约控制谁当前可修改对账记录，不能证明外部是否已接纳；接管者仍必须复用提交身份。

**练习：客户端 `learn-request-42` 与内部 `sweep:42` 有什么区别？**

答案：前者用于扫描受理请求去重，后者用于将该扫描可靠提交给 Durable。两层身份相关但用途不同，不能看到不同字符串就认为幂等失效。

### 场景 C：正文快照已保存，研究未完成时进程退出——第三、五天深入

**出事位置：**snapshot=301 与本轮绑定已提交，后续报告还未完成。

**重启怎么做？** 打开原业务库与执行库，恢复原任务。再次需要该 URL 时复用本轮固定快照 301；已确认成功的判断可复用。研究从实际检查点与工具记录继续，不保证任意内存局部变量原样存在。

**为什么不能重新抓最新页面覆盖 301？** 原引用与哈希针对旧正文。覆盖会使本轮前后使用不同材料，破坏解释与校验。

**练习：网页重启后改写了，原卡片依据哪份文字？**

答案：依据本轮绑定的原快照，而不是当前网页最新文本；新的抓取可以属于另一次工作，但不应原地改写旧绑定。

### 场景 D：供应商返回后、本地未确认就退出——第三、六天深入

**出事位置：**一次 Jev 调用可能已被供应商执行并收费，但本地成功记录尚未提交。

**系统知道什么？** 知道曾预约并发起尝试，但无法仅凭本地记录确认成功，可能保留 unknown。

**接下来怎么做？** 依重试、截止、预算规则决定是否再发请求；原尝试不自动退还预算。不能因没有本地成功结果就断言供应商未执行。

**练习：Pi Durable 能否保证这个窗口绝不重复计费？**

答案：不能。外部执行与本地确认不是共享原子事务，提交幂等也不覆盖所有供应商请求。

### 场景 E：子 Agent 引用了不存在的句子——第五天深入

**出事位置：**第 9 步将 quote 改成 `Version 2.4 is released.`，却仍引用原区间 `[0,25)`。

**系统怎么做？** 发现保存正文切片不等于提交 quote，该引用不能成为有效支持证据。没有其他有效支持声明时，不应发布为已核验新闻。

**语义变体：**若 quote 原样正确，但 claim 改成“OrbitKit 2.4 的恢复能力已在所有生产场景验证”，字符串匹配仍可能通过；其结论远超材料，需要语义支持判断，不能因为引用存在就算 supported。

**练习：引用匹配、来源支持、事实真实是什么关系？**

答案：引用匹配证明保存文本存在；来源支持判断文本与声明的关系；事实真实还取决于来源本身及独立核查。前两者不能自动证明第三者。

### 场景 F：用户在研究中取消——第四天深入

**出事位置：**研究子会话持有 epoch=0，用户取消扫描。

**系统怎么做？** 先持久改变业务状态、增加 epoch 为 1，再请求执行器中止。旧子任务再提交报告、发布或预约新请求时，受保护操作检查不通过。

**已经发送请求的结果怎么办？** 迟到 usage/费用可以审计结算，但不重新赋予业务写权限，也不能据此说供应商立即停算。

**练习：用户取消后无卡片，能叫 no_news 吗？**

答案：不能。它是取消流程，应按取消生命周期处理；没有新闻与没有完成研究不是一回事。

### 场景 G：调用预算耗尽——第六天深入

**出事位置：**研究想发起下一次请求，持久额度已经用完。

**系统怎么做？** 预约失败，不发送新请求，记录预算拒绝；最终核验保留该缺口。不能通过换工具名、无限修复或重启清零绕过预算。

**练习：已有一张卡片，预算耗尽后能直接说 completed 吗？**

答案：不能仅凭已有卡片判断。常规完成检查仍需看预算与其他缺口，修复耗尽且有可用结果时可能 partial。

## 五、第一天究竟需要答对什么？

### 1. 第一天必须做到

用自己的话讲清这条新闻的变化：

> 用户发起扫描，系统保存本轮身份与配置，把工作交给主 Agent。扫描子任务发现 OrbitKit 2.4，Jev 判断相关性和价值，程序处理事件关系并排序。主 Agent 把选中条目交给研究子 Agent；它读取正文、整理声明与引用，服务端核验后保存报告。再完成分类和发布检查，写入卡片，最后检查整轮是否还有缺口。

同时知道：不是每个步骤都由模型完成；发现文章不等于有发布证据；返回候选不等于整轮完成；运行中断后依持久记录恢复，不是所有内容从头再来。

### 2. 第一天不要求做到

- 背住具体表名、工具全部字段与所有调用次数。
- 背住 Jev 阈值及原始响应 Schema。
- 解释完整 leaseToken 条件更新或 epoch 传播实现。
- 分析每个崩溃窗口的事务边界。
- 运行演示、调试测试或现场定位代码。

这些有明确的后续学习日，不要把七天要求全部压到第一天。

### 3. 第一天下课验收：五题，每题 4 分

**题 1：第一次发现 OrbitKit 2.4 的是哪个环节？**

答案要点：gather；读取来源/搜索；解析并保存候选；尚未核验可发布。每个要点 1 分。

**题 2：Jev 和研究子 Agent 分别做什么？**

答案要点：Jev 接收明确材料；返回结构化判断；研究子 Agent 使用工具读取资料；组织分析与报告。每个要点 1 分。

**题 3：从候选到卡片还差什么？**

答案要点：按计划研究；正文与引用证据；HFS 分类；服务端发布检查。每个要点 1 分。

**题 4：`run_news_sweep` 返回后结束了吗？**

答案要点：没有；它主要结束四阶段扫描子任务；后面还有研究与发布；服务端最终核验决定整轮结果。每个要点 1 分。

**题 5：这条新闻沿途留下哪些信息？**

答案要点：扫描身份与上下文；条目与判断结果；正文/声明/研究报告；最终卡片与终态。每类 1 分。

16/20 分且没有“所有步骤都由 Jev 完成”“看到标题就直接发卡”“子任务返回等于整轮结束”这三类错误，即可通过本文第一天验收。技术名词暂时说成中文概念也可以。

### 4. 后续复习如何加深

第二次读每步“具体怎么做”和“保存什么”；第三次读异常场景。每次选一个场景，按下列顺序口述：

```text
当前在哪一步？
已经有了什么记录？
发生了什么异常？
系统能确认什么，不能确认什么？
根据什么继续、重试、拒绝或终止？
这次处理能保证什么，仍不能保证什么？
```

不要只背“有 Outbox”“有 checkpoint”“有证据链”，要将术语放回这个案例的具体数据变化中。
